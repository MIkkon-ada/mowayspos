# V2 前端体验改进方案

日期：2026-09-27
范围：V2 前端的信息架构、首页体验、项目工作入口与视觉一致性。本文是产品与交互改进建议，不包含代码实施。

## 一、目标与设计原则

系统由老板、PM 和项目成员共同使用，三类角色使用频率接近。工作以项目为单位展开，但个人日常优先处理自己负责的项目工作。首页因此不应强迫所有人使用同一种工作视角：老板先判断全局并统一调度，PM 先推进自己负责的项目，成员先完成自己承担的工作。三类角色共享项目上下文和导航规则，首页内容与优先动作按权限、项目角色调整。

设计原则：

1. 先回答“我现在应该关注什么”，再提供深入查看项目的入口。
2. 项目是工作组织的主线；个人待办是进入项目工作的快捷视角，不取代项目。
3. 重要状态必须有可解释的依据，点击状态或事项后能进入相应项目和处理流程。
4. 角色决定首页重点和可用动作；前端展示不替代后端权限校验。
5. 先调整信息层级和操作路径，再统一色彩、间距、字体和控件风格。

## 二、现状评估

### 已有基础

- 登录后会获取用户可见项目，每个项目记录当前用户的 `user_roles`；全局身份也包含 `is_ceo`、`can_view_all` 等字段，可支持首页分角色呈现。
- V2 已有老板/全局驾驶舱、项目健康、治理待处理事项和重点任务概览的实现基础。
- PM/项目角色可以汇总其负责或参与的项目；项目成员已有跨项目“我的任务”页面，并可从任务进入项目或提交汇报。
- 项目工作推进表已包含重点工作、关键任务、责任人、计划、状态、进展等信息，可作为项目内的管理视图。

### 主要体验问题

1. **首页选择逻辑与用户工作目标不完全吻合。**驾驶舱同时支持全局、我的项目、单项目和月份范围；有全局权限的用户默认进入全局范围，但界面没有先突出最需要注意的项目或行动。
2. **健康状态的可信度不足。**治理首页有健康状态展示，但当前 `DashboardPage` 对项目健康的前端推算主要依据完成率，未形成真正的风险判定；已有类型支持“风险”，当前生成项目健康行的逻辑却没有生成该状态。健康展示需要先定义可解释的数据规则。
3. **待处理事项只适合做摘要。**现有聚合逻辑按类别、截止时间排序后最多取 3 条行动和 6 条重点任务。它可作首页预览，不足以支撑老板完整调度或查看责任闭环。
4. **“我的任务”取数依赖姓名匹配。**当前列表通过当前用户姓名查询和过滤责任人。建议确认姓名唯一性、改名和同名情况下的可靠性；首页不能把空列表直接解释成没有工作，需区分“确实无任务”和“数据未加载/匹配失败”。
5. **导航按模块罗列，跨页操作成本高。**驾驶舱、工作推进表、我的任务、工作汇报、确认、会议、问题、成果、组织、项目管理等入口并列，用户需先理解模块再选择入口。
6. **工作推进表的视图控制占据较多注意力。**缩放、适合宽度、重置、行高、显示字段、自动列宽和导出等控件同时出现，主业务字段和任务操作的视觉优先级被稀释。
7. **视觉语言和文案层级不够一致。**全局浅蓝卡片风格与高密度表格并存；治理区还出现 Initiative、Evidence 等中英文混用。需要形成一套稳定的中文界面用词和页面层级。

## 三、目标信息架构

### 1. 老板：全局态势与统一调度

首页顺序建议：

1. **全局项目概览**：项目总数、健康/关注/风险/未启动数量，以及最近更新时间和健康判定口径入口。
2. **需要老板关注**：需要决策、跨项目/跨部门协调、重大风险、长期无进展等事项，按影响和紧迫度排序。每项至少呈现项目、事项、当前责任人、等待时长/截止时间、建议动作。
3. **项目组合列表**：可按健康、阶段、负责人、业务线筛选；行内显示状态依据、关键节点和最新变化。点击进入项目详情。
4. **调度跟进**：记录已作出的协调/决策、责任人、完成期限和后续状态，老板能检查调度是否闭环。

“项目健康”用于发现需要关注的项目；“待调度事项”用于决定下一步动作。两者相连：从风险项目定位到具体事项，再进入项目查看上下文、指定或确认责任安排，并追踪后续结果。

### 2. PM：负责项目推进

首页顺序建议：

1. **我负责的项目**：默认按风险、延期、临近节点排序；项目较少时直接展开，不强迫先选范围。
2. **本周推进重点**：即将到期、已延期、阻塞、待确认、长期未更新的工作。
3. **项目内工作入口**：工作推进表、问题与风险、待确认汇报、会议/变更记录等放在项目上下文中，避免从全局模块导航中猜入口。

PM 可以切换自己负责的项目，也能按需查看参与项目；跨项目任务汇总保留为快捷视图。

### 3. 成员：完成自己承担的项目工作

首页顺序建议：

1. **待我完成**：逾期、今天/本周到期、进行中、未开始，默认突出需行动的任务。
2. **所属项目上下文**：任务旁始终显示项目、重点工作、责任角色和计划时间；可一键进入该项目或汇报。
3. **我的项目**：作为项目切换和浏览入口，展示角色、阶段和近期节点；不代替待办首页。

### 4. 共用导航

建议稳定为三类一级入口：

- **工作台**：按角色呈现首页。
- **项目**：我的项目/项目组合；进入项目后显示项目内导航。
- **协作与管理**：汇报、确认、会议、问题、成果、组织和系统设置等，按权限收纳并提供待办数量。

移动端沿用同一信息架构，优先保证工作台、项目切换、待处理事项和汇报易达。

## 四、关键交互与数据规则

### 项目健康

不要仅用完成率判断健康。建议组合以下信号并展示原因：计划关键节点是否延期、关键任务是否逾期、风险/重大问题状态、最近进展更新时间、待决策/待确认阻塞。首版先展示“风险/关注/正常/未启动”和触发原因，不急于引入难解释的综合分数。健康规则由产品与业务确认后，优先在后端或统一领域逻辑中计算，避免不同页面各自推算。

### 调度事项

第一阶段使用系统现有的决策、协调、责任人确认等治理事项，统一成可筛选、可追踪的行动列表；不把现有“协调建议”擅自扩展为任意改派任务或人员。若要支持老板直接改派、跨项目分配资源或记录调度指令，需要先补充授权边界、通知规则、责任人接受/退回、审计记录和闭环状态，再作为独立能力实施。

### 角色与项目入口

- 全局身份（老板/公司管理）默认进入全局工作台；项目角色用户默认进入自己的项目工作台。
- 同一用户兼具多种角色时，首页同时保留全局视角与个人负责工作入口；用户可切换视角，且系统记住上次选择。
- 用户只有一个可访问项目时可自动进入；多个项目时展示项目总览/选择器，不悄悄跳入任意项目。
- 首页数据按当前用户权限取数；无权限、加载中、部分失败和确实无事项使用不同状态提示。

## 五、视觉改进方向

- 保留成熟企业软件的克制风格，降低装饰性渐变、过多圆角和卡片边框的重复使用。
- 明确页面标题、核心数字、主动作、次动作、筛选器和内容列表的字号与间距层级。
- 用颜色辅助表达状态，始终配合文字标签和原因，避免只靠红黄绿。
- 减少工作台首屏卡片数量；同一层级控制在 3–5 个重点模块，详情通过展开、筛选或进入项目查看。
- 工作推进表默认突出业务字段；低频的缩放、密度、列显示和列宽操作集中到“视图设置”，导出作为独立次级操作。
- 统一中文名词：建议将 Initiative 统一为“重点工作/关键任务”（按实际实体层级确定），Evidence 统一为“成果/佐证材料”，并清理技术术语直接暴露给业务用户的情况。

## 六、实施阶段

### 阶段 0：口径确认与数据核查

- 明确老板、PM、成员的身份字段和兼任角色优先级。
- 确认项目健康规则、风险事项来源、老板可执行的调度动作及权限边界。
- 核查我的任务按姓名匹配的唯一性，评估是否可改用稳定人员 ID。
- 盘点现有治理行动的完整字段、总数查询、跳转目标和更新能力。

### 阶段 1：工作台与导航重排

- 根据现有角色和数据做老板、PM、成员的角色化工作台。
- 老板首页优先展示项目组合与可执行治理事项；PM 首页突出负责项目与推进阻塞；成员首页突出责任任务和汇报。
- 将“我的项目”定位为项目列表/切换入口，不作为老板统一首页。
- 将全局模块导航归组；项目内操作在项目上下文中呈现。
- 统一空状态、加载状态、权限状态、部分失败提示和更新时间。

### 阶段 2：健康与待办可信度

- 建立有业务解释的健康规则和触发原因。
- 补齐待调度事项列表、筛选、排序、跳转和处理后状态刷新。
- 对多项目聚合展示总量和“查看全部”，首页不以固定 3 条作为完整清单。
- 强化任务责任人识别，避免姓名匹配造成遗漏或误认。

### 阶段 3：统一视觉与工作推进表

- 建立共享设计令牌：颜色、字体、行高、间距、边框、按钮等级和状态样式。
- 先在工作台和项目工作主路径应用，再逐步覆盖管理页和低频页。
- 将工作推进表默认视图改为业务优先，视图设置收纳低频控制；保留 Excel 导出与表格熟悉度。
- 做桌面端、窄屏和移动端的可用性检查。

## 七、成效判断

- 老板能在首页快速回答：哪些项目需要关注、原因是什么、我现在要协调/决策什么。
- PM 能快速找到自己负责项目中最需要推进的工作，并从提醒进入具体项目处理。
- 成员无需先理解模块分类，就能看到自己负责的任务、所属项目和汇报入口。
- 首页不把数据加载失败误显示为零事项；健康状态可以解释并可追溯。
- 使用者能在桌面和移动端稳定完成项目切换、任务查看、汇报和待确认处理。
- 通过短期可用性走查观察任务完成路径和误点情况；具体量化目标在基线测量后制定。

## 八、待确认事项

1. 老板的“统一调度”首期需要哪些实际动作：仅查看并进入现有流程，还是要直接下达指令/调整责任人/协调资源？
2. PM 的“负责项目”以项目负责人角色为准，还是统筹人也要作为同等主视角？
3. 项目健康规则由谁维护，项目级延期、风险和停滞阈值是否有公司统一口径？
4. 同一用户兼任老板、PM 或成员时，默认进入全局视角还是记住上次工作视角？
5. 老板首页需要查看全公司项目，还是还要按业务线/部门/客户组合筛选？

## 结论

建议以“角色化工作台 + 项目作为共同工作上下文”为总体方案。首期先利用现有项目、角色、任务和治理数据重排首页与导航；同时把健康判定和调度权限的业务口径确认列为前置事项。第二期再补足健康计算、完整调度清单及必要的闭环能力。这样可以先改善老板、PM、成员各自的首屏体验，又不会把未经确认的调度权直接写进系统。
