# 启动会确认 Agent 设计

## 目标

将启动会从可自由填写的会议类型升级为项目启动的必经确认流程。Agent 负责理解会议、比对会前工作推进表雏形并生成变更建议；PM 发起并提交，企业教练审核；只有审核通过的内容才能写入正式工作推进表并使项目进入执行中。

## 范围

本设计覆盖项目立项审核通过后的启动会、Agent 分析、人工审核、正式写入和生命周期流转。普通会议纪要保留为执行期的独立功能，但不能再伪造或替代启动会。

## 生命周期

新增 `pending_kickoff`（待启动会）状态：

```text
draft → dispatched → pending_review
pending_review --企业教练审核通过--> pending_kickoff
pending_kickoff --启动会审核通过且写入成功--> active
pending_kickoff --启动会退回--> pending_kickoff
pending_review --企业教练退回立项--> returned
```

- 企业教练审核立项通过后，项目不再直接进入 `active`，也不写入 `kickoff_date` / `kickoff_by`。
- `pending_kickoff` 项目不可提交正式工作汇报、不可执行期新增或派发关键任务。
- `active` 只表示启动会已完成审核，已批准的执行版工作推进表已落库。
- 项目结束、归档等现有后续生命周期保持不变。

## 角色与权限

| 动作 | PM / owner | 企业教练 / project_ceo | 普通成员 | 技术管理员 |
|---|---|---|---|---|
| 发起启动会 Agent | 可以 | 可以查看 | 不可以 | 可兜底 |
| 编辑会议原文及待审内容 | 可以 | 可以查看 | 不可以 | 可兜底 |
| 提交启动会审核 | 可以 | 不适用 | 不可以 | 可兜底 |
| 审核变更和启动结论 | 不可以自审 | 可以 | 不可以 | 可兜底 |
| 写入执行版并启动项目 | 由审核通过的事务执行 | 触发 | 不可以 | 可兜底 |

PM 不得审核自己提交的启动会。企业教练只能审核其所在项目的启动会。

## 启动会确认 Agent

Agent 不是单次 Prompt。它由可审计的阶段组成，每个阶段保存输入、输出和状态：

1. **材料准备**：读取项目立项资料、待审核时冻结的工作推进表雏形、项目成员、历史启动会草稿和会议原文/音频转写。
2. **会议理解**：提取会议基本信息、参与人、共识、待确认事项、决策、行动项和原文证据。
3. **计划比对**：将会议结论与会前的重点工作、关键任务、负责人、协助人、计划时间、完成标准逐项比较。
4. **变更提案**：输出新增、修改、删除和无变更四类结构化提案；每项必须携带会前值、建议值、理由和会议原文证据。
5. **规则校验**：校验成员归属、任务层级、负责人/协助人角色、日期格式、父子任务归属和空白必填项。校验失败项不能进入可批准集合。
6. **审核包生成**：生成可阅读的启动会纪要、执行版差异清单、风险与缺失项、"按雏形执行，无调整"结论（若无变更）。

Agent 不拥有直接写库权限，也不自行决定项目是否启动。每次运行产生一个版本化的审核包；重新分析或 PM 修改后产生新版本，旧版本保留审计记录。

## 审核与写入

1. PM 对 Agent 审核包进行补充或修正后提交。
2. 企业教练逐项批准、退回修改或驳回提案，并填写审核意见。
3. 所有阻断项被批准或明确驳回后，企业教练确认启动。
4. 后端在一个事务中：写入已批准的任务与关键任务变更、固化发布的启动会纪要、写入 `kickoff_date` 与 `kickoff_by`、将项目从 `pending_kickoff` 更新为 `active`、写入操作日志并发送通知。
5. 任一写入失败时事务回滚，项目保持 `pending_kickoff`，不产生半完成的执行版。

即使会议结论是无修改，也必须生成一条 `meeting_type=kickoff` 的已审核启动会纪要，并执行项目启动事务。

## 页面与入口

- 项目管理：企业教练审核立项通过后，项目显示“待启动会”，不显示“进行中”。
- 会议纪要页：先选项目；选择 `pending_kickoff` 项目时只可进入“启动会确认 Agent”，不展示会议类型选择；选择 `active` 项目时只能新建普通会议纪要。
- 启动会工作台：显示会议原文、Agent 纪要、会前雏形、结构化差异、校验结果、PM 提交动作和企业教练审核动作。
- 审核记录：可追溯 Agent 运行版本、PM 修改、教练意见、批准项、驳回项和最终写入结果。

## 数据与接口边界

- 继续使用 `Meeting` 保存启动会纪要，但新增启动会审核包、提案项、运行记录和会前快照的数据结构；不把临时 Agent 输出直接写进 `Task` / `SubTask`。
- 项目状态接口必须识别 `pending_kickoff`，并在汇报、任务结构写入、普通会议创建等接口执行服务端校验。
- 启动会专用接口应区分：创建草稿、运行 Agent、保存 PM 编辑、提交审核、教练审核、确认启动；每个写接口校验项目角色与当前状态。
- 旧的 `kickoff_project` 仅保留运维兜底，不作为正常界面流程；普通 `approve_project` 不再完成启动动作。

## 异常处理

- Agent 调用失败：保留原文和已保存草稿，允许重试，不改变项目状态。
- Agent 输出不符合结构：标记运行失败，不生成审核包。
- 会议无计划调整：生成“无调整”审核包，仍要求企业教练审核。
- 会议内容缺少启动所需信息：列为阻断项，企业教练不能确认启动，PM 补充后重新提交。
- 审核退回：项目保持 `pending_kickoff`，已批准项不写正式执行表。

## 验收标准

1. 立项审核通过后的项目进入 `pending_kickoff`，不会直接进入 `active`。
2. 只有 `pending_kickoff` 项目能创建启动会审核包；`active` 项目不能创建第二次启动会。
3. 启动会页面不提供人工会议类型选择。
4. Agent 输出包含可追溯的会前值、建议值和原文证据。
5. PM 提交后企业教练可逐项审核；PM 不能自审。
6. 任何未审核或被退回的提案均不修改正式任务数据。
7. "无修改"启动会同样经过审核，并在通过后将项目启动。
8. 启动成功时，批准变更、启动会纪要、项目状态、启动信息和操作日志在同一事务内完成。
9. 启动前，正式工作汇报与执行期任务派发被服务端拒绝；启动后恢复现有 `active` 权限。
