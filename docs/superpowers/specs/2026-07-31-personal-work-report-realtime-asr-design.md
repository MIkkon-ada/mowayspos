# 个人工作汇报实时转写优化设计

## 1. 背景

当前个人工作汇报页面通过浏览器麦克风采集音频，经 AudioWorklet 转换为
16 kHz 单声道 Int16 PCM，再通过 FastAPI WebSocket 转发到 DashScope
`paraformer-realtime-v2`，最终将增量识别结果写入工作汇报文本框。

现有链路已经具备实时出字能力，但存在以下风险：

- AudioWorklet 以约 8 ms 为一包发送音频，每秒产生约 125 次 WebSocket
  消息和后端线程切换，容易带来调度抖动与队列积压。
- 停止录音后，前端固定等待 1.5 秒便关闭连接，没有等待服务端明确完成，
  网络或模型回调稍慢时可能截断最后一句。
- 识别会话没有绑定当前项目和关键任务，模型无法利用项目名称、人名和任务
  名称纠正专业词。
- 运行日志缺少实际采样率、音频时长、队列峰值、首字延迟和停止收尾耗时，
  无法区分采集、传输、模型与文本合并问题。
- 录音期间用户编辑文本时，后续增量识别结果可能覆盖用户修改。

生产服务器按 2 vCPU、4～8 GB 内存规划，且没有确认存在 NVIDIA GPU，因此
本阶段不在生产服务器自托管 FunASR。继续使用 DashScope 云服务，并通过
DashScope 调用云端 `fun-asr-realtime`。

## 2. 目标

本阶段只优化“个人工作汇报”的实时转写，不包含会议实时转写。

目标包括：

1. 降低音频发送频率和服务端调度开销。
2. 使用明确的停止完成协议，避免丢失句尾。
3. 将当前项目、重点工作、关键任务和相关人员转换为受控识别上下文。
4. 通过 DashScope 云端 `fun-asr-realtime` 提升中文、噪声和专业词识别能力。
5. 保留 `paraformer-realtime-v2` 快速回退能力。
6. 将临时识别结果与稳定文本分离，避免文本抖动和重复追加。
7. 建立不记录原始音频和完整正文的可观测指标。
8. 保持现有“转写文本 → AI 提取 → 人工确认 → 提交”业务流程不变。

## 3. 非目标

本阶段明确不做：

- 会议纪要实时转写。
- 说话人分离。
- 在生产服务器部署 FunASR 模型权重。
- 自动保存原始录音。
- 语音识别完成后自动提交工作汇报。
- 通过语音识别直接修改任务状态、创建成果或创建问题。
- 录音进行到一半时切换识别模型。
- 新增语音识别管理页面。
- 重构现有工作汇报的 AI 结构化提取流程。

会议实时转写必须在个人工作汇报完成上线和验收后，作为独立设计与实施阶段
推进。

## 4. 方案选择

### 4.1 备选方案

#### 方案 A：保留 Paraformer，只修复传输与停止协议

优点是改动小、回归风险低；缺点是专业词和复杂声学环境下的准确率提升有限。

#### 方案 B：DashScope Fun-ASR + 传输修复 + 项目上下文

继续使用现有 DashScope API Key，不增加 GPU 和模型运维成本。采用云端
`fun-asr-realtime`，并将当前任务的结构化上下文传入识别会话。

#### 方案 C：方案 B + 停止后的文件精校

实时识别用于即时显示，停止后将完整录音再次提交非实时模型生成最终稿。准确率
上限最高，但会增加音频保存、费用、等待时间和隐私处理复杂度。

### 4.2 选择

本阶段采用方案 B。方案 A 作为回退开关；方案 C 留作后续增强，不进入本阶段
范围。

## 5. 用户流程

```text
选择项目
→ 选择要汇报的关键任务
→ 点击开始录音
→ 建立识别连接并加载任务上下文
→ 边说边显示文字
→ 停止录音并完成最后一句
→ 用户检查和修改文字
→ AI 提取结构化工作进展
→ 用户确认后提交
```

### 5.1 录音前置条件

开始录音必须满足：

- 已选择项目。
- 已选择当前要汇报的关键任务。
- 项目处于允许提交工作汇报的状态。
- 当前用户有权对该关键任务提交工作汇报。
- 浏览器支持麦克风和 AudioWorklet。
- 用户授予麦克风权限。

前端可以根据已加载数据提前禁用按钮，但后端必须重新验证项目和任务权限。

### 5.2 录音期间

前端分别维护：

- `confirmedText`：服务端已标记为最终句的稳定文本。
- `partialText`：当前尚未完成、允许模型持续修正的临时句子。

界面将临时句子显示为弱化样式。收到最终句后，将其移入稳定文本并清空临时
句子。录音期间文本框只读，防止用户修改被下一次增量结果覆盖。

### 5.3 停止后

停止期间显示“正在完成最后一句”，禁止重复点击。收到服务端 `done` 后：

- 关闭 WebSocket。
- 文本框恢复编辑。
- 用户可以修正人名、数字和专业词。
- 后续 AI 提取、人工确认和提交继续使用现有流程。

## 6. 总体架构

```text
VoiceUpdatePage 当前项目和关键任务
        │
        ▼
useVoiceRecorder
  ├─ 管理识别连接状态
  ├─ 合并 partial/final 文本
  └─ 控制麦克风开始与停止
        │
        ▼
AudioWorklet
  ├─ Float32 → Int16 PCM
  ├─ 聚合约 100 ms 音频
  └─ 计算基础音频质量指标
        │
        ▼
/api/transcribe/stream
  ├─ 会话认证
  ├─ 项目与任务权限验证
  ├─ 构建工作汇报识别上下文
  └─ 协调实时 ASR 会话
        │
        ▼
DashScope fun-asr-realtime
  ├─ partial 结果
  └─ final 结果
```

## 7. WebSocket 协议

协议采用有明确状态边界的消息流。

### 7.1 建立连接

服务端接受连接并完成登录校验后返回：

```json
{"type":"ready"}
```

### 7.2 启动识别

前端发送：

```json
{
  "type": "start",
  "scene": "work_report",
  "project_id": 12,
  "selected_task_id": 86,
  "sample_rate": 16000,
  "format": "pcm"
}
```

后端验证权限、构建上下文并成功启动模型后返回：

```json
{
  "type": "started",
  "model": "fun-asr-realtime",
  "session_id": "random-session-id"
}
```

前端只有在收到 `started` 后才开启麦克风和发送二进制音频，避免开头音频在模型
尚未就绪时丢失。

### 7.3 识别结果

服务端将 DashScope 回调标准化为：

```json
{
  "type": "transcript",
  "segment_id": "seg-18",
  "text": "本周已经完成成果库联调。",
  "final": true,
  "begin_time": 12600,
  "end_time": 15800
}
```

`segment_id` 在单次会话内唯一。前端使用它避免重连、重复回调或最终事件重放
造成文本重复。时间戳为可选字段，不作为本阶段界面功能依赖。

### 7.4 停止识别

用户点击停止后，前端立即停止麦克风，将不足 100 ms 的剩余 PCM 作为最后一包
发送，再发送：

```json
{"type":"stop"}
```

后端依次完成：

1. 停止接收新的二进制音频。
2. 排空待发送音频队列。
3. 调用 DashScope 会话的停止接口。
4. 等待最后一批识别回调完成。
5. 返回：

```json
{
  "type": "done",
  "session_id": "random-session-id",
  "duration_ms": 18320
}
```

前端收到 `done` 后才主动关闭 WebSocket。前端停止等待上限为 8 秒；超时后保留
所有稳定文本，并提示最后一句可能不完整。

### 7.5 错误协议

统一错误消息：

```json
{
  "type": "error",
  "code": "ASR_START_FAILED",
  "message": "语音识别服务启动失败，请重试",
  "retryable": true
}
```

前端展示面向用户的 `message`，日志使用稳定的 `code`。不得把 API Key、完整
上下文、供应商原始堆栈或内部路径返回给浏览器。

## 8. 音频采集与发送

### 8.1 音频格式

- 采样率：16 kHz。
- 声道：单声道。
- 编码：PCM Int16 little-endian。
- 目标包时长：100 ms。
- 正常包大小：约 3200 字节。

AudioWorklet 每次处理浏览器音频量子，但不再立即 `postMessage`。它将样本累积
到 1600 个后编码并发送。停止时发送剩余样本，不用静音填充。

### 8.2 浏览器音频约束

请求单声道，并默认启用浏览器的回声消除与噪声抑制。记录浏览器最终采用的
`MediaTrackSettings`，不能假定请求值一定生效。自动增益是否启用以 A/B 录音
结果决定，不在同一次上线中与模型切换同时调整。

### 8.3 背压

前端监控 `WebSocket.bufferedAmount`。当积压持续超过安全阈值时：

- 不丢弃已经采集的有声 PCM。
- 显示网络异常提示。
- 如果积压持续增长至不可恢复阈值，停止本次录音并保留稳定文本。

后端使用有上限的音频队列并记录队列峰值。队列写满不能静默丢帧，应结束会话并
返回可重试错误。

### 8.4 VAD 边界

浏览器侧可以计算音量和静音时长用于提示，但第一版不自动停止录音，也不删除
静音包。云端模型负责句子断句；用户的停止按钮负责结束整次工作汇报。

## 9. 工作汇报上下文

### 9.1 输入

上下文构建器接收：

```python
build_work_report_asr_context(
    current_user: str,
    project_id: int,
    selected_task_id: int,
) -> str
```

### 9.2 权限与数据来源

后端必须验证：

- 当前用户可访问该项目。
- `selected_task_id` 属于该项目。
- 当前用户对该关键任务具有工作汇报提交权限。

上下文只从后端数据库读取以下结构化字段：

1. 当前关键任务名称。
2. 关键任务所属重点工作名称。
3. 项目名称。
4. 当前任务责任人和协助人姓名。
5. 少量固定业务词汇。

不从前端接收任意热词或提示文本，不读取汇报正文、问题描述、附件、操作日志或
其他自由文本。

### 9.3 排序与长度

上下文按“当前任务 → 重点工作 → 项目 → 相关人员 → 固定术语”的顺序组织。
总长度限制在约 400 个字符。空间不足时先删除低优先级固定术语，不截断人名和
任务名称。

示例：

```text
当前项目：博维 AI 驾驶舱。
当前重点工作：成果库与工作推进页面升级。
当前关键任务：完成项目驾驶舱二期验收。
相关人员：张三、李明、王晓燕。
常用术语：Moways、关键任务、重点工作、成果入库、企业教练、项目统筹人。
```

上下文可按“用户 + 项目 + 当前任务”缓存 5 分钟。日志只记录上下文字符数和
词条数量，不记录完整内容。

## 10. 模型与配置

第一版使用后端环境配置，不新增管理页面：

```env
ASR_REALTIME_MODEL=fun-asr-realtime
ASR_CONTEXT_ENABLED=true
ASR_PACKET_DURATION_MS=100
ASR_STOP_TIMEOUT_SECONDS=8
ASR_HEARTBEAT_ENABLED=true
```

快速回退配置：

```env
ASR_REALTIME_MODEL=paraformer-realtime-v2
ASR_CONTEXT_ENABLED=false
```

模型切换只影响新连接。启动阶段若 Fun-ASR 失败，可以在麦克风尚未开启时尝试
一次 Paraformer 回退；一旦开始发送音频，本次会话不得切换模型。

DashScope API Key 继续使用现有安全配置来源，不发送到前端，也不在日志输出。

## 11. 模块边界

### 11.1 前端

`frontend/src/features/voice-update/useVoiceRecorder.ts`

- 管理连接与录音状态。
- 发送 `start` 和 `stop`。
- 收取标准协议消息。
- 管理停止等待与资源清理。

`frontend/src/features/voice-update/voiceRecorderProtocol.ts`

- 定义客户端与服务端消息类型。
- 提供协议解析和校验。
- 提供基于 `segment_id` 的文本合并逻辑。
- 不依赖浏览器音频 API，允许 Node 单元测试。

`frontend/public/worklets/pcm-audio-processor.js`

- 转换 PCM。
- 聚合约 100 ms 音频包。
- 发送最后剩余包。
- 计算 RMS、峰值和削波指标。

现有个人工作汇报页面只消费录音 Hook 暴露的状态，不直接实现 WebSocket 协议。

### 11.2 后端

`bowei_ai_dashboard/app/routers/transcribe.py`

- WebSocket 认证和协议协调。
- 验证消息顺序与基础字段。
- 调用上下文与 ASR 服务。
- 输出标准化错误。

`bowei_ai_dashboard/app/services/realtime_asr.py`

- 封装 DashScope 实时识别会话。
- 发送音频、停止会话并等待完成。
- 将供应商回调转换为内部事件。
- 收集会话指标。

`bowei_ai_dashboard/app/services/asr_context.py`

- 验证项目、任务与用户权限。
- 查询允许发送的结构化字段。
- 构建和缓存个人工作汇报上下文。

会议转写未来可以复用 `realtime_asr.py`，但必须使用独立的会议场景上下文策略，
不能扩展 `build_work_report_asr_context` 承担会议职责。

## 12. 状态机

前端状态：

```text
idle
→ connecting
→ starting
→ recording
→ stopping
→ completed
```

任一活动状态均可进入 `failed`。只有：

- `starting` 收到 `started` 才能进入 `recording`。
- `recording` 发出 `stop` 才能进入 `stopping`。
- `stopping` 收到 `done` 才能进入 `completed`。

组件卸载、用户切换项目或任务、浏览器隐藏页面导致媒体轨道结束时，必须统一清理
麦克风、AudioContext、Worklet 和 WebSocket。

## 13. 故障处理

### 13.1 启动失败

- 麦克风尚未开启时直接返回 `idle` 或 `failed`。
- 显示可重试错误。
- 不清空用户原有文本。

### 13.2 录音中断线

- 立即停止麦克风和 Worklet。
- 保留所有 `final=true` 的稳定文本。
- 临时文本单独标记为可能不完整，不自动并入稳定文本。
- 不自动重连继续同一段录音，避免重复或缺口无法判定。

### 13.3 停止超时

- 8 秒内未收到 `done` 时主动关闭连接。
- 保留稳定文本。
- 提示“最后一句可能不完整，请检查后再提交”。

### 13.4 页面离开

- 统一关闭媒体轨道和音频上下文。
- 不在后台继续录音。
- 草稿保存继续遵循现有个人工作汇报草稿机制。

## 14. 隐私与日志

第一阶段默认不保存原始录音。每次识别生成随机 `session_id`，记录：

- 用户、项目和任务 ID。
- 模型名称。
- 音频包数量和音频总时长。
- 音频队列峰值。
- 首次 partial 延迟。
- 首次 final 延迟。
- 停止到 `done` 的耗时。
- 最终句子数量。
- DashScope 请求 ID 和稳定错误码。
- 上下文字符数和词条数量。

不记录：

- API Key。
- 原始 PCM 或录音文件。
- 完整转写正文。
- 完整识别上下文。

## 15. 分阶段上线

为隔离变量，按以下顺序上线：

1. 增加当前 Paraformer 链路的指标，形成基线。
2. 继续使用 Paraformer，只上线 100 ms 分片与 `done` 协议。
3. 保持传输协议不变，将指定测试用户切换到 Fun-ASR。
4. 确认模型稳定后，为测试用户开启任务上下文。
5. 完成固定语料和真实用户验收后，再扩大使用范围。

每一阶段必须支持独立回退，不把分片、模型和上下文三个变量一次性全量上线。

## 16. 测试与验收

### 16.1 自动化测试

前端测试覆盖：

- 协议消息解析。
- partial 替换而非重复追加。
- final 按 `segment_id` 去重。
- `done` 前不关闭连接。
- 启动失败不清空已有文本。
- 停止超时保留稳定文本。
- Worklet 将多个音频量子聚合为约 100 ms 包。
- 停止时发送剩余样本。

后端测试使用模拟 DashScope 会话覆盖：

- 未登录连接拒绝。
- 无项目权限时拒绝启动。
- 任务不属于项目时拒绝启动。
- 无汇报权限时拒绝启动。
- 成功的 `ready → start → started → binary → stop → done` 顺序。
- 非法消息顺序返回协议错误。
- 音频队列排空后才停止模型。
- 模型启动异常标准化为安全错误。
- 回调异常传递给前端并记录请求 ID。
- 上下文长度、字段范围和缓存键符合设计。

### 16.2 固定语料

准备至少 20 条固定测试语料，覆盖：

- 项目名称和成员姓名。
- 重点工作和关键任务名称。
- 日期、金额和百分比。
- 中文夹杂英文品牌词。
- 1～3 秒自然停顿。
- 句末立即点击停止。
- 普通办公室背景噪声。

每条保留人工校对的标准文本，用同一录音比较不同阶段，避免说话差异干扰结果。

### 16.3 验收指标

- WebSocket 音频消息从约 125 次/秒降到约 10 次/秒。
- 20 次固定语料测试不出现句尾截断。
- 不出现 final 句重复追加。
- 首次出字延迟 P95 不高于约 1.5 秒。
- 点击停止到 `done` 的 P95 不高于约 3 秒。
- 项目专业词识别率相对 Paraformer 基线明显提升。
- 无权限用户不能通过伪造 `project_id` 或 `selected_task_id` 获取上下文。
- DashScope 异常不清空已经确认的文字。
- 原有上传音频转写、AI 提取、人工确认和最终提交不受影响。

## 17. 发布与回退

发布前先保留 Paraformer 配置。出现以下任一情况时，将新会话回退到
`paraformer-realtime-v2` 并关闭上下文：

- Fun-ASR 启动失败率持续高于现有基线。
- 首字延迟或停止收尾延迟明显恶化。
- 固定语料准确率低于现有基线。
- 发现上下文越权或隐私风险。
- 生产服务器音频队列持续积压。

协议和 100 ms 分片修复可与模型回退独立保留；除非证据表明协议本身引入问题，
否则不因模型回退撤销已验证的传输改进。
