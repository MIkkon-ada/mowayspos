# 会议纪要成员进度审核设计

**日期：** 2026-08-10  
**状态：** 待用户审阅

## 目标

在启动会审核通过的任务计划基础上，每次保存进度会议纪要后，自动识别每位成员的工作完成情况和任务汇报，生成带原文证据的待审核结果；负责人确认后，系统才写回对应子任务状态。

## 范围

本次升级包含：

- 使用已批准的启动会 Agent 任务计划作为正式基线；
- 保存进度会议纪要后自动触发成员进度分析；
- 要求会议转写使用“姓名：汇报内容”格式进行成员归属；
- 持久化成员进度分析结果、证据、建议状态和人工审核记录；
- 在会议纪要详情页逐条确认、忽略或修改后确认；
- 仅在人工确认后更新子任务状态并记录操作日志。

本次不包含：

- 自动说话人分离或声纹识别；
- AI 直接修改任务状态；
- 对历史会议进行无基线的批量回溯；
- 引入后台任务队列或新的异步基础设施。

## 现状依据

- 普通会议分析入口为 `POST /api/meetings/analyze`，已有 `progress` 模式和成员进展提取能力；
- 启动会审核通过后，`KickoffAgentRun.snapshot_json` 保存审核前冻结计划，确认启动时应用批准的变更；本次升级会新增 `approved_snapshot_json` 保存最终批准后的任务计划；
- 当前 `Meeting` 未持久化 `reports_json`，且分析接口不会保存原始 AI 运行记录；
- 当前任务推送流程会直接逐条创建或更新子任务，因此本次审核写回必须明确独立的确认边界。

## 方案

### 1. 基线

选择项目最近一次 `KickoffAgentRun.status = approved` 的 `approved_snapshot_json` 作为基线。基线中的任务和子任务必须属于当前项目，并保存以下快照字段：

- 任务/子任务 ID；
- 标题；
- 负责人；
- 计划时间；
- 验收标准；
- 启动会审核通过时的原始快照。

`snapshot_json` 继续保留用于审计 Agent 当时看到的原始计划；确认启动并应用批准提案后，重新读取项目任务生成 `approved_snapshot_json`，该字段不可被后续进度更新覆盖。

如果项目没有已批准的启动会基线，分析接口返回可识别的业务错误，会议纪要仍然可以保存，但不创建进度审核结果。

### 2. 触发链路

前端保存进度会议纪要时执行两个独立请求：

1. 创建或更新会议纪要，状态保持 `draft`；
2. 调用成员进度分析接口；
3. 分析接口读取已批准启动会基线和当前项目成员；
4. 将原文按 `姓名：内容` 解析为成员汇报段落；
5. 将每个成员的汇报与其基线任务匹配；
6. AI 返回结构化状态、证据引用、差距和建议写回状态；
7. 后端校验成员、任务 ID 和证据引用后保存 `pending` 结果；
8. 前端展示待审核结果。

分析失败不回滚已经保存的会议纪要，也不修改任何任务；用户可以重试分析。

### 3. 状态和证据

每个成员-任务结果使用以下状态：

- `completed`：汇报明确说明已经完成；
- `in_progress`：明确说明正在进行；
- `blocked`：明确说明遇到阻塞；
- `not_started`：明确说明尚未开始；
- `not_mentioned`：原文没有涉及该任务。

AI 必须返回短的原文 `evidence_quote`。无法从原文确认时，不得推断为完成、进行中或阻塞。分析结果同时保存 `confidence` 和校验错误列表，供审核页展示。

### 4. 数据结构

新增成员进度审核结果表（建议命名 `meeting_progress_reviews`），至少包含：

- `id`、`project_id`、`meeting_id`；
- `member_name`；
- `baseline_run_id`、`baseline_task_id`、`baseline_subtask_id`；
- `baseline_snapshot_json`；
- `report_text`、`status`、`evidence_quote`；
- `suggested_task_status`；
- `review_status`（`pending`、`accepted`、`ignored`）；
- `reviewed_by`、`reviewed_at`、`review_comment`；
- `validation_json`、`created_at`、`updated_at`。

同一会议、同一成员、同一基线子任务只允许存在一条当前审核结果；重试分析时生成新的分析版本或覆盖未审核结果，但不得覆盖已确认的历史审核记录。

### 5. 审核和写回

会议详情页增加“成员完成情况”模块，展示基线任务、本次汇报、判断状态、证据和当前任务状态。

负责人可逐条：

- 确认并写回；
- 忽略；
- 修改建议状态/备注后确认。

写回规则：

- `completed`：更新子任务为已完成；
- `in_progress`：更新子任务为进行中；
- `blocked`：保留任务状态并追加阻塞备注；
- `not_started`：保持未开始；
- `not_mentioned`：不修改任务。

写回前重新校验任务仍属于当前项目且未删除。写回与审核状态更新在同一数据库事务中完成；任何一项失败则整条确认失败，不留下“已确认但未写回”的状态。

### 6. 权限

- 进度分析沿用会议纪要的项目访问权限；
- 查看草稿和审核结果沿用现有会议草稿可见规则；
- 确认并写回仅允许项目负责人或现有任务写权限角色；
- 每次确认写回都调用现有操作日志机制。

## 接口草案

- `POST /api/meetings/{meeting_id}/progress-review/analyze`：基于已保存会议和已批准启动会基线生成待审核结果；
- `GET /api/meetings/{meeting_id}/progress-review`：读取当前会议的成员审核结果；
- `PATCH /api/meetings/{meeting_id}/progress-review/{review_id}`：修改审核状态、建议状态和备注；
- `POST /api/meetings/{meeting_id}/progress-review/{review_id}/confirm`：事务性写回子任务并标记为已确认。

分析接口必须返回明确的 `no_baseline`、`no_speaker_prefix`、`invalid_evidence` 等业务错误，而不是把无法判断的情况伪装成完成状态。

## 前端交互

- 保存进度会议后显示“正在生成成员完成情况”；
- 没有启动会基线时显示说明，不阻塞会议纪要保存；
- 分析结果按成员分组，每个任务独立审核；
- 已确认结果只读，显示确认人和确认时间；
- 分析失败提供“重新分析”按钮；
- 原文区域保留证据引用定位信息，至少能回看对应汇报段落。

## 验收标准

1. 有已批准启动会基线时，保存格式正确的进度会议会生成 `pending` 成员任务结果。
2. 每条结果都包含成员、基线任务、状态和原文证据；无法确认时为 `not_mentioned` 或待人工确认，不得臆测完成。
3. 没有已批准启动会基线时，会议仍能保存，分析结果明确提示缺少基线。
4. 没有“姓名：”前缀的段落不会被错误归属给项目成员。
5. 忽略结果不会修改任务。
6. 确认结果会更新正确子任务，并产生操作日志。
7. 写回失败时审核结果不会被标记为已确认。
8. 重试分析不会覆盖已经确认的历史结果。
9. 现有普通会议、启动会审核和任务推送测试继续通过。

## 测试策略

- 服务层单元测试：基线读取、姓名前缀解析、状态归类、证据校验、缺少基线处理；
- 路由测试：权限、分析失败不影响会议保存、审核确认事务；
- 数据模型测试：唯一性、历史结果不可被重试覆盖；
- 前端测试：保存后触发分析、待审核列表、确认/忽略和失败重试；
- 回归测试：现有会议草稿、发布/退回、启动会确认启动、任务卡推送流程。
