# OwnerSubmitModal 项目方案编排工作台 UI 重构设计

## 1. 背景与目标

本设计基于 `codex/main-after-pr` 分支的整合提交 `800135c0429391eeff240f4018ace3b057fe9b8c`，目标文件为：

`frontend/src/features/settings/OwnerSubmitModal.tsx`

现有页面业务能力完整，本次只重构前端页面骨架、信息层级、密度和重点工作的展开/折叠交互。页面由“大型立项表单弹窗”调整为“以重点工作和关键任务为核心的项目方案编排工作台”。

## 2. 实施方案

采用单文件优先方案：在现有 `OwnerSubmitModal.tsx` 内重排 JSX 和 Tailwind class，并增加最少量的本地 UI state。不抽取 Picker，不新增路由，不新增全局样式；只有 Tailwind 无法表达页面专用样式时才允许向 `frontend/src/styles.css` 添加严格限定作用域的样式。

技术上继续使用 Modal，视觉上改为接近全屏的单列工作台。桌面端最大宽度约 1560px、高度约 92～94vh，四周保留 16～24px 空间，弱化遮罩、圆角和阴影。

## 3. 页面结构

页面按以下顺序纵向排列：

1. 工作台 Header
2. 横向项目资料摘要
3. 工作推进方案 Header 与局部操作
4. AI 面板（打开时）
5. AI 合并预览（存在时）
6. 重点工作列表
7. 新增重点工作入口
8. sticky 底部提交操作栏

取消 `owner-submit-workbench-columns` 的桌面左右分栏，不再保留 280～300px 的独立项目资料侧栏。关键任务表格在窄屏时允许自身横向滚动，但工作台本身不得产生页面级横向滚动。

## 4. Header 与项目资料摘要

Header 标题改为“填写项目方案 — {project.name}”，副说明为“完善项目计划内容，确认后提交企业教练审核”。保留“待负责人完善”状态，右侧只保留关闭操作。

项目资料摘要位于工作推进方案上方，采用低高度横向布局：

- 项目名称：只读文本，不使用 disabled input。
- 项目周期：继续使用 `projectPeriod` 及现有解析、组合逻辑。
- 项目完成准则：继续绑定 `fillForm.objectives`，压缩输入高度但不改变绑定逻辑。
- 更多项目资料：继续使用现有 `<details>`，入口改为低强调的“更多项目资料”，展开后保留客户名称、项目类型、项目背景和补充说明。

项目资料摘要默认高度控制在约 120～150px，不成为页面第一视觉主体。

## 5. 工作推进方案

工作推进方案是页面第一视觉主体。说明文案统一为：

“规划重点工作方向，并拆解关键任务、负责人、协助人、时间和验收标准。”

`AI 分析文件 / AI 草稿` 与 `+ 新增重点工作` 保留在工作推进方案的局部 Header。AI 按钮使用浅紫背景和轻边框；新增重点工作使用白色或浅灰次级按钮，两者都不与橙色提交按钮竞争视觉优先级。

`OwnerSubmitAiPanel` 继续显示在工作推进方案 Header 下方。AI 合并预览的计数、warnings、取消和确认合并行为保持不变，仅允许轻量调整视觉。

## 6. 重点工作展开与折叠

新增本地 UI state：

```ts
const [expandedTaskIndexes, setExpandedTaskIndexes] = useState<Set<number>>(
  () => new Set([0]),
)
```

也可以使用行为等价且更稳定的实现，但状态只存在于前端，不进入 API 或后端。

### 6.1 默认状态

- 页面首次打开时，第一个重点工作展开。
- 其他重点工作默认折叠。
- 不采用强制单选手风琴，允许保留多个已展开项。

### 6.2 折叠态

折叠态完全只读，不渲染名称、目标、关键任务对应的 input、Picker 或日期控件。单行至少展示：

- 两位编号，例如 `01`、`02`。
- 重点工作名称；空值显示“未命名重点工作”。
- 目标成果摘要；空值显示“未填写目标成果”。
- 当前 `task.subtasks.length` 对应的关键任务数，例如“4 个关键任务”。
- “展开”操作。
- 弱化的 `···` 结构菜单，菜单内提供“删除重点工作”。

点击折叠卡片主体或“展开”均进入编辑态。菜单操作必须阻止事件冒泡，避免点击删除菜单时意外展开。

### 6.3 展开态

展开态 Header 使用单行主结构：编号、重点工作名称、目标成果/验收标准、收起与弱化结构操作。名称和目标输入高度约 38～40px，采用轻边框和两级 focus ring，不使用强阴影。

展开态下继续显示关键任务表格及新增关键任务入口。删除默认使用灰色弱化样式，仅在 hover 时呈现红色。

### 6.4 新增、删除与索引修正

调用现有 `addTaskDraft()` 后，新建项自动展开，已有展开状态保持不变。

删除重点工作后必须重算 `expandedTaskIndexes`：

- 删除索引之前的展开索引不变。
- 被删除项的索引移除。
- 删除索引之后的展开索引统一减一。
- 不得发生展开错位或另一项意外切换状态。

### 6.5 AI 合并后的展开策略

AI 合并不得把全部新增重点工作展开。应用合并结果后保持仍然有效的当前展开状态，并最多自动展开一个需要继续检查的新重点工作。若没有新增项，则不额外改变展开状态。

## 7. 关键任务表格

保留现有六列及业务含义：关键任务、负责人、协助人、时间段、验收标准/备注、操作。

桌面端列宽按信息重要性重新分配，目标比例约为：

- 关键任务：26%
- 负责人：14%
- 协助人：16%
- 时间段：15%
- 验收标准/备注：24%
- 操作：5%

关键任务与验收标准获得最大空间。删除备注列现有的 `max-w-[180px]` 和 `truncate` 限制，placeholder 改为“填写验收标准或说明”。表头、行内 padding 和输入框高度统一压缩，单行目标高度约 44～52px。

表格仍保留合理的 `min-width`，窄屏只在表格容器内部横向滚动。

## 8. 必须原样保留的功能

以下能力只允许因布局需要微调视觉 class，不改变行为或数据流：

- `AssigneePicker`：Portal、搜索、人员加载状态和单选逻辑。
- `HelperPicker`：Portal、多选、搜索、已选人数、清空，以及排除当前负责人的逻辑。
- `fetchPeople()`、`people`、`peopleLoading`、`peopleError`。
- `OwnerSubmitAiPanel`、AI 草稿生成与合并预览。
- `toCurrentDraft`、`toSubmitDraft`、`buildAiMergePreview`、`applyMergedDraftToForm`、`currentAiDraft` 的现有数据逻辑。
- warnings、AI audit、audit retry，以及业务提交成功但审计失败时禁止重复提交的恢复机制。
- 新增重点工作、新增关键任务和现有删除行为。
- `composeProjectPeriod`、`parseProjectPeriod`、`parsePeriodValue`、`composeTaskPeriod`、`updateSubTaskPeriod`。
- `handleSubmit` 的人员加载、重点工作、关键任务、负责人和 AI audit 校验顺序。
- `ownerSubmitProfile`、`applyInitAnalysisRun` 及成功回调。

本次不新增“保存草稿”。

## 9. 明确禁止的改动

不修改后端、数据库、migration、API 路径、API payload、项目生命周期、角色、权限、企业教练审核、项目派发、ProjectsMgmtSection 主流程、项目路由或工作推进表正式执行页。

不增加第四层数据结构，不重新定义重点工作和关键任务的业务语义，不重构或拆分 Picker。

## 10. 测试与验收

先检查现有相关结构测试；针对本次已确认的新交互补充或调整测试断言，确认新断言在旧实现上因缺少目标结构或交互而失败，再进行页面实现。不得删除测试、放宽为无意义断言或修改无关测试。

自动验证至少包括：

- `frontend/tests/ownerSubmitModalLayout.test.mjs`
- `frontend/tests/ownerSubmitAiIntegration.test.mjs`
- 前端现有全部 Node 结构测试
- `npm run build`，必须同时通过 `tsc -b` 与 `vite build`

结构测试覆盖：

- 单列工作台和横向项目资料摘要。
- 第一项默认展开、折叠态只读和空值占位。
- 新增项自动展开且不重置已有状态。
- 删除前方重点工作后的索引修正。
- AI 合并后最多自动展开一个新增项。
- 关键任务列宽及验收标准不再被 180px/truncate 限制。
- Picker、AI 合并、AI audit 与提交校验标志仍然存在。

手工验收覆盖 1440px、1600px 和 1920px 桌面宽度，并验证：

- 无工作台级横向滚动。
- 项目资料横向展示且没有独立左侧栏。
- 折叠态不出现可编辑控件。
- 点击卡片主体和展开按钮可进入编辑态。
- 新增重点工作只自动展开新增项。
- 删除重点工作后展开状态不串位。
- AssigneePicker、HelperPicker、AI 面板、AI 合并和 audit retry 可正常操作。
- 未选择负责人时仍提示“请选择关键任务负责人”。
- 正常提交仍进入原企业教练审核流程。

## 11. 完成标准

完成后应只有 OwnerSubmitModal 相关前端文件及直接相关测试发生变化；后端、API、数据库和业务流程改动均为“否”。页面第一眼应突出重点工作和关键任务执行方案，而不是项目表单字段。

## 12. 视觉收口补充（f67803d 之后）

本轮不改变上述页面架构和交互，只完成三项视觉收口：

- 未展开“更多项目资料”时，横向项目资料摘要控制在约 120～150px 内；保持三列、两行完成准则和原数据绑定。
- 顶部“新增重点工作”继续作为正式入口；列表底部改为紧贴列表、全宽、无阴影的弱化“＋ 继续新增重点工作”，继续调用原 `addTaskDraft()`。
- 内容较少时保留工作台自然空白，不使用 `min-height`、`flex-grow`、加高卡片或占位内容填充。

重点工作折叠、索引修正、AI 合并身份映射、Picker、AI 与提交逻辑全部禁止修改。真实视觉验收必须使用本地 UI state 建立三个重点工作，形成一项展开、两项折叠，并在 1440、1600、1920px 检查页面级横向滚动、信息密度和列表扫描性。
