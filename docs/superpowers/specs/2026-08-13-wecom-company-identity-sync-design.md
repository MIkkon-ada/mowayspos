# 企业微信公司身份同步设计

## 目标

为人员资料增加企业微信通讯录同步能力，自动维护公司部门和岗位信息，同时允许管理员在本系统中对部门或岗位分别进行本地覆盖。该功能只维护公司身份资料，不改变系统权限角色、项目角色、项目可见性或决策流程。

## 边界

### 纳入

- 从企业微信通讯录读取成员 `userid`、姓名、部门和职位。
- 通过 `userid` 优先匹配本地人员；姓名只作为待确认的辅助匹配。
- 支持管理员预览同步结果并确认写入。
- 记录企业微信原始值与当前生效值。
- 部门和岗位分别支持本地覆盖、恢复企业微信值。
- 保留企业微信账号登录、账号绑定和通知能力。
- 保留 Excel/手工维护作为备用路径。

### 不纳入

- 不根据企业微信岗位自动授予系统权限。
- 不根据部门或岗位自动分配项目角色。
- 不删除本地人员、账号、项目成员或历史业务数据。
- 不在本阶段做企业微信通讯录写回。
- 不在本阶段实现定时任务或事件回调；先提供管理员手动同步，后续可扩展。

## 数据模型

现有 `Person.department` 继续作为当前生效部门字段，现有 `Person.role` 保持兼容并继续作为历史职务描述。新增字段：

- `position_title`：当前生效岗位。
- `wecom_userid`：人员级企业微信唯一标识，支持无本地账号人员先完成身份同步。
- `wecom_department`：企业微信最新部门路径文本。
- `wecom_position_title`：企业微信最新岗位。
- `department_source`：`wecom` 或 `local`。
- `position_source`：`wecom` 或 `local`。

同步规则：

1. 以 `wecom_userid` 匹配 `Person`；没有稳定 ID 时不自动按姓名写入，只返回建议匹配。
2. 新人员默认使用企业微信部门和岗位，来源标记为 `wecom`。
3. `department_source=local` 时，企业微信部门只更新原始值，不覆盖当前部门。
4. `position_source=local` 时，企业微信岗位只更新原始值，不覆盖当前岗位。
5. “恢复企业微信值”把对应当前值替换为最新原始值，并将来源改回 `wecom`。
6. 现有人员首次接入时保留当前资料，只有管理员在同步预览中确认后才建立或更新企业微信映射。
7. 离职或停用成员只标记为待处理/可停用，不做自动删除。

## 后端接口

- `GET /api/accounts/wecom-directory`：读取企业微信通讯录详情和部门名称，生成同步预览。
- `POST /api/accounts/wecom-directory/sync`：按预览确认结果写入人员资料和企业微信映射。
- `POST /api/people/{id}/identity-reset`：按字段恢复企业微信值，支持 `department` 或 `position`。

现有 `/api/accounts/wecom-users` 和批量账号绑定接口保持兼容。企业微信通讯录拉取从简化成员列表扩展为成员详情列表，并新增部门列表读取；企业微信配置和通讯录读取权限不足时返回明确错误。

## 前端操作

人员管理页增加“企业微信通讯录”入口：

1. 点击“读取通讯录”。
2. 展示新增、可匹配、已同步、待确认和冲突记录。
3. 管理员确认匹配关系和需要写入的人员。
4. 点击“确认同步”。
5. 人员卡片展示当前部门/岗位、来源和企业微信最新值。
6. 本地修改部门或岗位后显示“本地覆盖”。
7. 提供“恢复企业微信值”操作。

系统权限角色和项目角色继续在原有入口维护，不能由企业微信同步结果覆盖。

## 测试与兼容

- 企业微信服务层测试成员详情和部门数据解析。
- 后端测试按 `userid` 匹配、预览、确认同步、本地覆盖和恢复企业微信值。
- 测试同步不会修改 `system_role`、`ProjectMember.role` 或项目历史关系。
- 前端结构测试覆盖同步入口、预览状态、本地覆盖和恢复操作。
- Alembic migration 必须兼容 SQLite 和 PostgreSQL。
- 同步接口保持管理员权限校验，不暴露企业微信 Secret。
