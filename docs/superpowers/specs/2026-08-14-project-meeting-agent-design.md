# 项目会议纪要 Agent 接管设计

## 1. 目标

第一阶段只改造“项目会议纪要”流程。用户选择项目并上传已经整理好的 `.docx` 会议纪要后，由 Meeting Agent 读取会议文档和项目上下文，完整理解会议事实，生成结构化会议纪要草稿及执行安排变更建议。项目负责人审核通过前，Agent 不得修改工作推进表。

启动会 Agent、个人工作汇报 Agent、实时语音和音频转写不在本阶段范围内。

## 2. 已确认决策

1. 项目必须先选择，项目 ID 是权限、上下文、任务匹配和回填的边界。
2. Word 文档是本次会议事实的唯一来源；项目上下文只能帮助理解和匹配，不能补造会议事实。
3. 不再使用固定标题、表头或关键词规则提取会议基本信息、议程、总结、决议和待办。
4. Word 读取器只负责安全地读取段落、表格、顺序和文本位置，不解释业务含义。
5. Agent 负责理解全部会议内容，并通过只读工具查询项目资料。
6. Agent 输出必须符合严格的结构化契约；结构化契约是程序接口，不是规则提取。
7. Agent 只能提交草稿和变更建议。项目负责人逐项审核后，系统才能事务性回填工作推进表。
8. 第一场会议不要求上期纪要、上周待办或历史进展；没有历史资料不是失败条件。
9. 每条会议事实和每条可回填建议必须携带会议原文证据；缺少证据时进入待确认，不得执行。
10. 模型不可用、输出不合规或达到循环上限时，保留原始 Word 和失败记录，不再使用规则提取结果兜底生成草稿。

本设计在“新上传的项目会议纪要”路径上取代 `2026-08-12-standard-meeting-minutes-fidelity-design.md` 中的标准 Word 业务字段规则提取。历史记录中的 `standard_minutes` 数据继续兼容读取，但新流程不再产生该模式。

## 3. 技术路线

第一阶段采用现有 FastAPI 与模型配置体系，自研一个供应商无关的 Meeting Agent 编排器，并使用 Pydantic 定义工具参数、运行事件和最终输出。暂不引入 LangGraph，以免在业务契约尚未稳定时同时迁移运行框架。

编排器必须与模型供应商解耦。DeepSeek、通义、GLM 或其他 OpenAI 兼容模型继续通过现有 `AIService` 和 `meeting.analysis` 能力策略调用。后续如果需要长时间暂停、分布式恢复或多 Agent 协作，可以在不改变工具和输出契约的前提下把编排层替换为 LangGraph。

## 4. 总体架构

```text
项目 + Word 原文件
        |
        v
文档读取层
只读取内容、结构和位置，不解释字段
        |
        v
Meeting Agent 编排器
  - 系统提示词
  - 只读项目工具
  - 最多 6 个推理/工具步骤
  - 结构化最终输出
        |
        v
确定性安全校验
  - JSON/Pydantic 契约
  - 原文证据位置
  - 项目和任务 ID 归属
  - 可写字段白名单
  - 日期和权限约束
        |
        v
会议草稿 + 变更建议
        |
        v
项目负责人审核
  |                 |
  v                 v
退回并记录原因      批准选中建议
                    |
                    v
              单事务回填 + 发布
```

## 5. Agent 运行协议

### 5.1 输入

每次运行冻结以下输入：

- `project_id`；
- 原始 Word 文件 ID、文件哈希和提取后的文档内容；
- 上传人和运行时间；
- Meeting Agent 版本、提示词版本；
- 项目上下文工具可访问的项目范围；
- 若用户填写了会议类型，则作为用户输入传入，不覆盖文档事实。

Agent 不在初始提示词中接收整库数据。它先接收项目摘要和工具清单，再按需要调用工具取得人员、任务、子计划、历史进展或历史会议，避免超长上下文和过期数据。

### 5.2 工具

第一阶段只提供只读工具：

| 工具 | 作用 | 主要返回值 |
| --- | --- | --- |
| `get_project_profile` | 查询所选项目基本信息 | 项目名称、目标、周期、状态、负责人 |
| `list_project_members` | 查询项目人员 | 人员 ID、姓名、项目角色、是否有效 |
| `search_plan_nodes` | 按会议表述检索工作推进表 | 重点工作、关键任务、执行安排及匹配分数 |
| `get_plan_node_detail` | 获取一个候选任务的完整上下文 | 父子关系、负责人、计划时间、完成标准、当前状态 |
| `get_recent_progress` | 查询指定任务近期已确认进展 | 已审核进展、实际产出、风险、更新时间 |
| `get_previous_meetings` | 查询历史已发布会议 | 会议日期、决议、行动项；首场会议返回空列表 |

工具层必须再次校验 `project_id` 和当前用户权限。Agent 不能传入其他项目 ID，也不能通过工具写数据库。

### 5.3 循环

Agent 每一步只能返回以下两种信封之一：

```json
{
  "type": "tool_call",
  "tool": "search_plan_nodes",
  "arguments": {
    "project_id": 1,
    "query": "完善会议纪要流程"
  }
}
```

```json
{
  "type": "final",
  "result": {
    "meeting_info": {},
    "summary": "",
    "agenda_items": [],
    "decisions": [],
    "completed_items": [],
    "next_steps": [],
    "risks": [],
    "open_questions": [],
    "task_updates": []
  }
}
```

编排器执行合法工具调用，把结果追加到同一次运行上下文，再调用模型继续判断。最多允许 6 个步骤；重复相同工具参数、调用未知工具、跨项目查询或超过上限时，运行失败并保存审计轨迹。

### 5.4 最终输出契约

会议基本信息由 Agent 从文档语义中提取：

```json
{
  "meeting_info": {
    "title": "",
    "meeting_date": "",
    "meeting_type": "",
    "location": "",
    "host": "",
    "participants": [],
    "organizer": "",
    "copied_to": []
  }
}
```

`meeting_info` 的每个非空字段也必须在运行结果中关联至少一条 Word 原文证据；展示层可以只显示字段值，但审计层必须保存字段级证据。项目名称、当前负责人或文件名不能替代会议文档中的基本信息。

会议事实统一使用以下结构：

```json
{
  "content": "会议中明确表达的事实",
  "evidence": [
    {
      "quote": "Word 中连续的原文",
      "char_start": 120,
      "char_end": 145
    }
  ],
  "confidence": 0.96,
  "needs_confirmation": false
}
```

每条 `task_updates` 使用以下结构：

```json
{
  "action": "update_execution_schedule",
  "target": {
    "project_id": 1,
    "workstream_id": 10,
    "key_task_id": 21,
    "execution_schedule_id": 31
  },
  "before": {},
  "proposed": {
    "status": "进行中",
    "progress_note": "",
    "actual_output": "",
    "title": "",
    "assignee_id": null,
    "start_date": null,
    "due_date": null,
    "expected_output": "",
    "completion_criteria": ""
  },
  "evidence": [],
  "reason": "",
  "confidence": 0.0,
  "needs_confirmation": true
}
```

允许的动作仍只有：

- 更新已有 `ExecutionSchedule`；
- 在已有 `SubTask` 下新增 `ExecutionSchedule`。

本阶段不允许删除计划、创建重点工作、创建关键任务、修改项目成员、跨项目迁移或直接修改父级任务。

## 6. Agent 与确定性代码的边界

“不使用规则提取”不等于删除所有程序校验。

Agent 负责：

- 理解 Word 的标题、表格和自然语言；
- 判断哪些内容属于基本信息、议程、决策、已完成、下一步和风险；
- 根据语义选择需要查询的项目工具；
- 把会议内容匹配到可能的工作计划节点；
- 解释匹配理由并给出置信度；
- 对缺失或冲突信息生成待确认项。

确定性代码只负责：

- 读取 Word 内容；
- 执行 Agent 请求的只读函数；
- 校验 JSON 类型和必填字段；
- 校验证据确实出现在原文位置；
- 校验人员、任务和子计划 ID 属于当前项目；
- 校验可写字段、日期格式和状态值；
- 保存运行轨迹、审核记录和版本；
- 审核通过后执行数据库事务。

代码不得根据标题、关键词、表头、编号或正则表达式决定会议字段的业务含义。

## 7. 数据与审计

继续复用：

- `MeetingDocumentSource` 保存原始 Word；
- `ProjectMeetingRun` 保存一次文档处理运行；
- `Meeting` 保存当前会议投影；
- `MeetingChangeSet` 和 `MeetingChangeProposal` 保存待审核变更；
- `MeetingReviewEvent` 保存提交、批准、退回和执行记录；
- `MeetingRevision` 保存不可变会议版本。

为 `ProjectMeetingRun` 增加或补齐以下审计信息：

- Agent 状态与当前步骤；
- 提示词版本；
- 模型代码；
- 每次模型调用的 invocation log ID；
- 工具调用轨迹；
- 原始模型响应；
- 结构化结果与校验结果；
- 安全错误码和失败阶段。

`source_mode` 对新 Agent 生成的会议继续使用兼容值 `ai_analysis`，前端展示名称改为“Agent 分析”。历史 `standard_minutes` 记录保持可读，不批量改写。

## 8. 接口与页面行为

### 8.1 新建流程

新建会议纪要页面保留：选择项目、会议类型、上传 Word。上传后直接创建 `POST /api/meetings/document-runs`，由 Agent 负责生成全部会议字段。前端不再调用标准纪要规则结果预填基本信息。

分析期间显示当前阶段：读取文档、理解会议、查询项目、匹配计划、校验结果、生成待审核草稿。完成后进入现有待审核页面。

### 8.2 审核流程

项目负责人可以：

- 编辑会议基本信息和总结；
- 查看每条事实的原文证据；
- 接受、修改或忽略每条任务变更；
- 对待确认项补充答案；
- 批准或退回；
- 退回时必须填写原因。

负责人补充的内容标记为 `human_input`，不得伪装成 Word 原文事实。重新分析时保留旧版本和退回记录。

### 8.3 写回

批准动作只确认会议内容和所选变更。执行写回前重新读取当前任务状态并与冻结快照比较；目标被修改、删除、归档或权限失效时，整个事务失败，不产生部分写入。写回成功后发布会议版本并允许下载 DOCX。

## 9. 异常处理

- Word 无法读取：保存上传记录和错误，允许更换文件。
- Agent 模型不可用：运行标记失败，保留 Word，不生成规则兜底草稿。
- Agent 返回非法信封：允许同模型一次格式修复；仍失败则结束运行。
- 工具参数非法或越权：拒绝执行，记录安全错误，不向模型泄露项目外数据。
- 达到 6 步仍未返回最终结果：运行标记 `step_limit_exceeded`，允许用户重试。
- 证据不存在或位置不符：该事实或变更标记待确认；可保存草稿，不可执行回填。
- 无法匹配任务：保留为待确认项，不自动创建父级任务。
- 第一场会议无历史数据：工具返回空列表，Agent 正常继续。
- 审核退回：保留当前版本、退回人、原因和时间，修改后创建新版本。

## 10. 测试策略

### 单元测试

- Pydantic 工具参数和最终输出契约；
- Agent 工具白名单、项目边界和循环上限；
- 重复工具调用检测；
- Word 证据位置校验；
- 任务 ID、人员 ID 和可写字段校验；
- 第一场会议空历史；
- 模型格式修复和失败状态。

### 集成测试

- 上传用户提供的第一场会议 Word，Agent 返回完整基本信息；
- Agent 调用项目工具并将“本周已完成、下周待办”匹配到已有关键任务的执行安排；
- 模型不可用时不触发标准 Word 规则兜底；
- 未审核前工作推进表没有变化；
- 负责人只批准部分建议时只执行选中项；
- 目标快照冲突时事务整体回滚；
- 退回原因和会议版本可追溯；
- 下载 DOCX 与已审核版本一致。

### 前端测试

- 上传后不使用 `standard_minutes` 预填；
- 分析阶段和失败原因正确显示；
- Agent 提取的基本信息、证据、待确认项和变更建议可见；
- 只有项目负责人可批准、退回和执行；
- 退回原因必填。

## 11. 验收标准

1. 上传 `AI升级项目周会-会议纪要-20260727.docx` 后，主题、日期、地点、类型、主持人、参会人员、整理人和抄送均由 Agent 正确展示。
2. 第一场会议没有上期纪要或上周追踪时仍能完成分析。
3. Agent 能看到项目人员、重点工作、关键任务、执行安排和当前进展，并按需调用查询工具。
4. Agent 能把文档中的本周已完成和下周待办匹配到已有关键任务下的执行安排，无法确定时明确标记待确认。
5. 新上传流程不调用标准纪要业务字段规则解析，也不以规则结果覆盖 Agent 输出。
6. 每条可执行变更都包含有效项目内目标 ID、前后值、理由、置信度和 Word 原文证据。
7. 项目负责人审核前，工作推进表不发生变化。
8. 退回必须记录原因；批准后只写回负责人选中的建议。
9. 写回失败不产生部分更新。
10. 审核通过的会议纪要可下载，且与保存版本一致。

## 12. 非目标

- 不改造启动会 Agent；
- 不改造个人工作汇报 Agent；
- 不实现实时语音或音频转写；
- 不实现多 Agent 协作；
- 不在第一阶段引入 LangGraph；
- 不允许 Agent 直接写数据库；
- 不自动创建重点工作或关键任务；
- 不删除历史 `standard_minutes` 记录。
