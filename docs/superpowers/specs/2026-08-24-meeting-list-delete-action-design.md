# 会议纪要列表删除操作设计

## 目标

让具备项目负责人或技术管理员权限的用户，可在会议纪要列表直接删除不再需要的会议记录；保留现有后端审计和权限校验，不新增 API。

## 界面与交互

桌面端会议列表的每一行「操作」列固定为：`查看 ｜ 编辑 ｜ 删除`。

- 移除目前只作展示、没有点击行为的 `…`。
- 「删除」使用红色文字按钮，置于「编辑」之后；项目归档时不显示该操作。
- 仅项目负责人（`owner`）或技术管理员能看到「删除」。后端仍是最终权限边界。
- 点击删除后，弹出原生确认框：`确认删除会议纪要「{title}」吗？此操作不可恢复。`
- 用户取消：不发起请求，列表不变。
- 用户确认：调用既有 `DELETE /api/meetings/{id}`；请求期间避免重复点击。
- 成功：从当前前端列表移除该条、若它正被选中则清空选择，并显示“会议纪要已删除”。
- 失败：保留该条记录并显示接口返回的错误信息；例如无权限、项目归档或记录已被他人删除。

## 数据与权限

复用 `DELETE /api/meetings/{id}`。该接口已要求登录、项目负责人角色、项目处于可写状态，并写入 `meeting_delete` 审计日志；此次不改变删除语义或数据表。

前端在 `meetings.ts` 增加与现有 API 封装一致的 `deleteMeeting(id)`，列表页调用它并更新本地状态。

## 测试与验收

新增前端结构/行为测试，覆盖：

1. 操作列包含「查看、编辑、删除」，不再渲染静态 `…`。
2. 删除按钮仅对项目负责人或技术管理员且项目未归档时出现。
3. 取消确认不会调用删除请求。
4. 确认后调用删除接口，并从列表中移除记录；失败时保持记录并提示失败。

后端既有删除路由无需改动；执行相关后端删除权限测试与前端测试集，确保 API 约束不回退。

## 范围外

- 不在详情页新增删除入口。
- 不实现回收站、恢复、批量删除或物理文件清理策略。
- 不为 `…` 新增低频菜单项目。
