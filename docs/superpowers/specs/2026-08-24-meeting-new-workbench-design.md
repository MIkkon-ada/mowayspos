# 新建会议纪要工作台设计

**状态：已确认，待编写实施计划。**

## 目标

将“新建会议纪要”完整工作台的首步视觉与交互对齐用户提供的参考图，同时保留既有 Word 上传、项目会议 Agent 分析、待核实和确认保存的业务链路。

## 范围

- 顶部采用标题栏、四步进度条和固定底部操作栏：会议设置与材料、AI 生成草稿、确认待核事实、确认保存。
- 首步采用“会议信息”和“会议材料”两张卡片，字段顺序和三列布局与参考图对齐。
- 会议日期改为原生 `date` 控件，支持日历选取。
- 主持人和整理人均从当前项目成员中单选；保存到既有 `host`、`organizer` 字符串字段。
- 参会人员继续保持可填写多人姓名的既有字符串字段。
- 新建时抄送默认写入“项目全体成员”；保存到既有 `copied_to` 字符串字段，且允许用户修改。
- 会议材料仅保留 `.docx` 上传、已上传状态、替换文件和“AI 生成草稿”动作。

## 实现边界

- 在 `NewMeetingModal` 加载当前项目成员，复用 `GET /api/projects/{id}/members`，将成员姓名作为主持人和整理人的单选项。
- 不修改后端接口、数据库 schema、既有会议字段名、Agent 流程或审核/保存语义。
- 编辑既有会议时保持原有字段值；默认抄送只应用于新建表单。
- 不实现真实消息发送或通知订阅；“项目全体成员”是会议纪要中的默认抄送文本。

## 交互与状态

1. 打开新建工作台时，加载项目成员并初始化 `copied_to` 为“项目全体成员”。
2. 用户选择会议日期、主持人、整理人，填写主题、地点和参会人员；主持人和整理人一次只能选择一名成员。
3. 用户上传 Word 后，现有上传状态更新；点击“AI 生成草稿”后沿用现有轮询和错误提示。
4. 分析、待核实和保存步骤继续使用已有内容与状态，不改变其接口调用顺序。

## 错误处理

- 成员加载失败时，表单不阻断；主持人和整理人仍显示为可编辑的单行输入，已有文本不丢失。
- 无项目成员时，单选控件显示无可选成员，不自动猜测人员。
- 继续沿用文件格式、上传、Agent 分析和保存的现有错误提示。

## 测试与验收

1. 新建表单使用日期选择控件，并保留 `meeting_date` 提交字段。
2. 主持人和整理人为单选控件，选项来自项目成员查询；参会人员不受此限制。
3. 新建表单的 `copied_to` 默认值为“项目全体成员”，编辑记录不覆盖已有抄送值。
4. 页面包含参考图所需的标题栏、四步条、会议信息卡、会议材料卡和固定底部操作栏的结构锚点。
5. Word 上传、Agent 运行和保存请求的现有参数不发生变化。
6. 前端单元测试和生产构建通过。

## 非目标

- 不改变会议详情、项目选择页或其他页面的布局。
- 不引入多选主持人/整理人、人员角色限制或实际抄送通知。
- 不改变后端对会议元数据的校验规则。
