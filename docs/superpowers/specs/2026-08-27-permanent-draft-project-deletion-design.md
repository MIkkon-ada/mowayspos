# 草稿测试项目永久删除设计

## 目标

让技术管理员能够从项目管理页永久删除测试用的草稿项目，并在同一数据库事务内清理该项目的业务关联数据。项目一旦删除不能从应用内恢复。

## 范围与权限

- 仅 `is_tech_admin`（项目能力中的 `super_admin`）可调用删除接口和看到删除入口。
- 仅生命周期为 `draft` 的项目可删除。`dispatched`、`active`、`pending_close`、`ended`、`archived` 一律返回 409，不显示前端入口。
- 不提供批量删除、按名称模糊删除或绕过二次确认的接口。

## 用户交互

1. 技术管理员在草稿项目卡片的 `⋯` 菜单中点击红色“永久删除项目”。
2. 对话框明确展示项目名称和不可恢复警告，并列出即将清理的关联数据计数（成员、重点工作、关键任务、附件、AI 分析记录等）。
3. 管理员输入与项目名称完全一致的文字；输入不匹配时删除按钮保持禁用。
4. 前端向 `DELETE /api/projects/{project_id}` 发送确认名称。成功后关闭对话框、刷新项目列表并提示成功；403、404、409 和网络错误均保留对话框并展示后端错误。

## API 与数据删除

新增受保护端点 `DELETE /api/projects/{project_id}`，请求体包含 `confirm_name`。服务端必须再次检查权限、项目存在性、草稿状态与确认名称；绝不依赖前端限制。

删除在一个事务中执行，先删除依赖行、后删除项目主记录。处理直接以 `project_id` 关联的业务记录，包括：

- 项目成员及成员变更申请；
- 重点工作（`tasks`）、关键任务草稿及其执行事件；
- 更新提交、会议、会议文档与会议/AI 分析、评审、变更集、启动智能体运行记录；
- 项目成果、成果提交和成果附件；
- 项目立项附件与立项 AI 分析运行记录；
- 问题、项目结束申请，以及其他由模型显式以 `project_id` 关联的项目业务行。

删除顺序必须考虑这些行之间的外键；任一步失败时回滚整个事务。业务审计日志不作为项目业务数据删除：删除成功后保留一条不含敏感快照的 `delete_project` 审计记录，用于追踪执行人、项目 ID 与名称。

## 失败处理

- 非技术管理员：403。
- 项目不存在：404。
- 非草稿项目或确认名称不匹配：409/422，且不做任何删除。
- 数据库异常：回滚、记录服务端异常，向前端返回安全的失败信息。

## 测试与验收

后端采用内存 SQLite 测试：验证技术管理员能删除草稿及其直接关联数据、普通用户被拒绝、非草稿被拒绝、确认名称错误不删除、任意异常回滚。前端测试验证仅技术管理员的草稿项目显示危险操作，确认文字不匹配时禁用，成功时刷新列表。

验收时在本地 8011 服务使用一个新建草稿测试项目执行完整删除流程；不对截图中的现有项目执行删除，除非用户在功能完成后单独指定并确认该项目。
