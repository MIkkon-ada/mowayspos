# 审核材料关键任务字段映射设计

## 背景

项目审核材料中的工作推进表按三层结构展示：专项、重点工作、关键任务。现有审核页在构造关键任务行时，错误使用了重点工作（`Task`）的 `collaborators` 和 `completion_standard` 字段；同时，导入兼容逻辑会把协助人写入关键任务的 `notes`，从而造成“协助人”列为空、备注列却出现协助人。

## 已确认的业务规则

- 专项对应项目层级。
- 重点工作对应 `Task` 层级，只提供该组关键任务的分组、目标成果和兜底信息。
- 每一行关键任务对应 `SubTask` 层级；负责人、协同成员、计划时间和完成标准均属于这一行。
- 关键任务的项目级读取接口返回 `collaborator_ids`，但不返回姓名数组；审核页必须用已加载的 `ProjectMember.person_name_snapshot` 按 ID 解析姓名。`collaborator_ids` 是唯一权威来源，不能由展示名称数组覆盖。
- 协助人之间使用“、”连接，无法解析的结构化 ID 不应改写或虚构名称。
- `notes` 中只用于兼容旧数据的单行“协助人：姓名…”不能作为备注显示。若同一备注还包含其他文本，保留其他文本。
- 对历史数据，若没有 `collaborator_ids`，允许从旧的“协助人：…”备注中回退显示；新格式以结构化 ID 为准。
- 无关键任务的占位行不显示重点工作的协助人，统一显示“—”。
- 完成标准优先取关键任务的 `completion_criteria`；仅当其为空时回退到重点工作的 `completion_standard`，保证旧数据仍可阅读。该值显示在关键任务行的“备注/标准”列；若有真实备注，两个值同时保留。
- 重点工作标题区只展示其目标成果（`key_achievement`），不再把重点工作的完成标准冒充为每行关键任务的验收标准。

## 方案比较

1. 继续使用重点工作字段：实现最少，但违反行级归属，不能解决截图问题。
2. **采用关键任务结构化字段并兼容旧备注（选择）**：与数据模型一致，能显示现有导入人员，也不会丢失历史文本。
3. 仅从备注解析协助人：能修复截图，但绕过已存在的结构化字段，未来编辑和接口数据会再次不一致。

## 实现边界

只调整审核视图的纯前端行构造逻辑，并增加覆盖结构化数据、旧备注回退、备注清理和完成标准优先级的回归测试。不修改已保存的项目、成员或导入流程。

## 验收条件

对“AI测试项目”中已有协助人的关键任务，审核材料的“协助人”列显示对应姓名；“备注/标准”列不再只显示重复的“协助人：…”文本。没有协助人的关键任务显示“—”，现有真实备注保持可见。
