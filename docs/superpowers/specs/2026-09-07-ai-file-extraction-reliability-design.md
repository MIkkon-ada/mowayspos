# AI 文件提取兼容性收口设计

## 目标

消除 AI 文件输入入口的格式承诺与实际能力差异；让扫描版 PDF 能在已配置的项目立项 Vision 模型下生成可审核草稿。

## 范围

- 会议纪要前端开放后端已支持的 `.docx`、`.txt`、`.xlsx`。
- 立项附件在当前解析环境缺少 `antiword` 时不再以模糊“无法解析”失败，而是返回可操作的缺失依赖说明；Docker 继续安装该依赖。
- 前端使用一个格式配置模块复用各入口的 `accept` 字符串和显示文案。
- 对纯扫描、没有文字层的项目立项 PDF，使用 Poppler 有限页渲染为 PNG 并调用现有、明确 opt-in 的项目立项 Vision 模型。

## 数据流

项目立项 PDF 仍先走 `pypdf` 文字提取。若该文件未提取出任何文字块，则创建仅包含页号的可追溯来源块，并把最多 8 页临时 PNG 交给 Vision。模型输出仍经过既有的草稿 schema、人员匹配、证据定位和人工审核流程；临时 PNG 在调用结束后删除。若模型未配置或调用失败，流程保留文本路线并标记需要审核，不会把图片内容写进日志。

## 非目标

- 不为工作汇报、会议纪要或关键任务计划新增 OCR。
- 不将原始附件内容、渲染图片或模型密钥写入审计日志。
- 不改变项目方案的业务字段、路由、审批逻辑或 AI 草稿应用方式。

## 验收

- 会议页面可选择并成功发送 `.txt`、`.xlsx`。
- `.doc` 缺少解析依赖时给出明确环境提示；Docker 镜像仍包含 `antiword`。
- 扫描 PDF 仅在文本为空时触发 Vision，页数、图像尺寸和像素总量受限，且临时目录被清理。
- 现有文字 PDF 保持纯文本路线。
- 前后端格式配置与各入口测试均通过。
