# 项目立项 AI 分析韧性设计

## 目标

让项目立项资料分析优先使用主模型完成复杂资料理解，同时避免备用模型故障使用户被动等待数分钟；对于结构完整的 Excel，跳过不必要的模型调用并直接生成可审核草稿。

## 范围

本次只调整 `project.init.analysis` 能力的调用与路由策略，不改变项目、任务、附件或审核的持久化字段，也不改变用户确认后才应用草稿的流程。

## 调用策略

该能力的主模型使用 200 秒单次超时。每个备用模型使用 25 秒单次超时。模型按既有优先级顺序调用：主模型超时、连接失败、限流或返回无效结构时，才尝试下一个备用模型。

超时属于单次模型请求限制，不改变上传文件的 25 MiB 单文件、100 MiB 总文件限制，也不改变分析任务的 30 分钟失效租约。

## 文件路由

只包含结构化 Excel 工作表范围的附件先运行既有确定性表格提取。若它能提取出至少一项任务，则直接返回 `structured-spreadsheet-fallback` 草稿，不调用模型；若不能形成有效草稿，才进入模型链路。

Word、PDF、文本文件、混合资料，以及需要视觉复核的复杂 Excel 或扫描 PDF，仍进入模型链路。复杂 Excel 和扫描 PDF 保留现有渲染图片与视觉模型路径；视觉模型不可用时回落到文本模型，并将需要复核的路由信息返回界面。

## 输出约束与可观测性

所有聊天模型请求都请求 JSON 对象输出。服务端仍将模型输出视为不可信内容：它必须包含一个可解析的 JSON 对象，并通过既有草稿结构校验、来源证据校验和人员匹配。

当模型返回内容不合格时，不保存原始回复，避免把可能含有业务资料的模型原文写入日志。改为在调用日志中记录脱敏诊断代码：`json_missing_or_multiple`、`json_malformed`、`schema_invalid` 或 `source_evidence_invalid`。前端在“查看分析信息”中显示这些代码及模型、耗时和是否发生回退，便于区分超时与格式问题。

## 批次合并

资料文本仍以每批最多 40,000 字符切分。多批完成后，先用本地标题归一化与相似度判断是否存在跨批重复候选；仅检测到候选冲突时才调用最终合并模型。没有冲突时直接合并确定性结果，省去一次模型请求。

## 错误处理

模型超时、连接失败、限流或无效输出均可回退。所有模型均失败时，若附件是可确定性解析的 Excel，则返回本地提取结果；否则保留现有失败状态和安全的用户提示。模型失败不会修改项目、任务或成员数据。

## 验收标准

1. 主模型的项目立项分析请求可持续最多 200 秒，备用模型最多 25 秒。
2. 完整的结构化 Excel 不调用聊天模型，直接返回可审核草稿。
3. 模型请求均包含 JSON 对象响应约束。
4. 无效模型输出可显示脱敏的具体诊断代码，不记录原始响应。
5. 多批且无重复候选时不会发起最终合并模型调用；有冲突时保留最终合并调用。
6. 现有视觉分析、来源追溯、审核确认与失败安全行为保持可用。
