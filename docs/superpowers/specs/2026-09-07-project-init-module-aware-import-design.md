# 项目立项 AI 模块化导入设计

## 目标

让项目立项资料导入支持一个或多个文件、一个或多个 Sheet，并由 AI 按业务语义将内容分流为“项目基本信息”和“工作推进方案”。用户确认预览结果后，基本信息写入项目立项表单，工作推进方案写入负责人推进表，避免把所有内容都误当成任务。

## 当前问题

现有项目立项 AI 草稿只有 `tasks` 结果，分析提示词也主要面向工作推进表。即使上传文件同时包含项目名称、背景、目标、周期和任务表，AI 也只会尽量把内容归纳为重点工作和子任务；项目基本信息没有独立结果，也没有独立预览和写入路径。

现有工作推进任务的语义识别、人员匹配、证据校验和提交事务已经可用，本次不重写这些能力，只在其外层增加项目基本信息模块。

## 范围

包含：

- 扩展项目立项 AI 草稿协议，新增 `project_profile`。
- 让 AI 识别 Sheet、区域和单元格内容所属业务模块，而不是依赖固定字体或表头。
- 支持多个附件结果合并，并保留文件名、Sheet、单元格范围等证据。
- 前端按模块展示识别预览，分别应用到项目基本信息和工作推进方案。
- 对已有项目资料执行安全合并：空字段补全，非空字段显示变更并需人工确认。
- 为模块路由、合并规则、历史响应兼容和关键页面交互增加测试。

不包含：

- 不改变现有项目生命周期状态值和接口路径。
- 不改变已有任务、子任务、人员匹配和证据字段的业务含义。
- 不自动绕过用户确认直接修改项目或任务正式数据。
- 不新增独立的 AI 服务接口；继续使用现有上传、分析运行、预览和应用链路。

## 业务模块

### 项目基本信息

识别并建议填入项目立项资料的字段：

- `name`：项目名称。
- `background`：项目背景、立项原因、现状问题。
- `objectives`：项目目标、建设目标、预期达成目标。
- `expected_outcomes`：预期成果、预期收益、交付结果。
- `start_date`：项目开始日期。
- `end_date`：项目结束日期。
- `description`：项目说明、范围、补充说明。

项目编号、项目状态、创建人、创建时间等系统字段不由 AI 生成。

### 工作推进方案

沿用当前任务草稿协议，识别：

- 重点工作 / 工作模块作为父级工作项。
- 关键任务作为父级工作项下的子任务。
- 目标、推进流程、验收标准、负责人、协助人、时间、状态、优先级和证据。

## AI 输出协议

分析结果扩展为：

```json
{
  "project_profile": {
    "name": "",
    "background": "",
    "objectives": "",
    "expected_outcomes": "",
    "start_date": "",
    "end_date": "",
    "description": "",
    "confidence": 0.0,
    "evidence": [],
    "warnings": []
  },
  "tasks": [],
  "warnings": [],
  "provider": "",
  "model_name": ""
}
```

`project_profile` 中每个非空字段必须带有可验证证据；AI 不得凭空生成日期、人员或项目名称。无法确定字段归属的内容进入 `warnings` 或模块级待确认列表，不得静默丢弃。

为兼容历史分析运行记录：

- `project_profile` 缺失时按空对象读取；
- 只有 `tasks` 的历史结果仍可正常展示和应用；
- 旧客户端发送的工作推进草稿格式继续有效。

## 数据流

```text
选择一个或多个文件
  → 上传并建立分析快照
  → 读取各文件各 Sheet 的结构、合并关系、原始单元格和位置
  → AI 判断内容属于项目基本信息、工作推进方案或待确认
  → 服务端验证 JSON、日期、长度、证据和人员匹配
  → 模块化预览
  → 用户确认基本信息变更和任务重复项
  → 基本信息进入项目表单草稿，工作推进方案进入负责人表单草稿
  → 用户保存或提交时沿用现有正式写入事务
```

服务端仍是最终边界。AI 只生成建议，不直接写入正式项目数据。

## 合并规则

- 当前项目基本信息为空、AI 有可信值：预览为“补充”。
- 当前项目基本信息非空、AI 值相同：预览为“无变化”。
- 当前项目基本信息非空、AI 值不同：预览为“变更”，默认不覆盖，必须人工选择。
- AI 没有证据或字段无法验证：预览为“待确认”，不能自动应用。
- 工作推进方案继续使用现有重复任务决策：新增、忽略、补充；已有任务不被静默删除。
- 多文件或多 Sheet 对同一字段提供多个值时，按证据完整度和置信度排序，并展示冲突值供人工选择。

## 前端设计

AI 面板的预览阶段增加模块摘要：

```text
文件分析完成
├─ 项目基本信息：识别 6 项，待确认 1 项
├─ 工作推进方案：识别 5 项重点工作、23 项关键任务
└─ 待确认内容：2 项
```

预览区使用两个可切换的内容区：

1. “项目基本信息”：按字段显示当前值、AI 建议值、来源证据和应用决策。
2. “工作推进方案”：保留现有重点工作、关键任务、人员、时间、目标、验收标准、推进流程和重复决策。

应用按钮明确拆分为：

- `应用基本信息`：只更新当前页面的项目资料草稿，不直接调用正式项目更新接口。
- `应用到推进表`：沿用现有任务草稿合并逻辑。

如果当前入口是负责人完善页面，只显示基本信息的只读建议或“申请修改”，不允许负责人无审批修改项目核心字段。项目创建/编辑页面可以消费同一份 `project_profile` 预览并由立项人确认保存。

## 后端边界与错误处理

- Pydantic 严格校验新增模块结构和字段长度。
- 证据必须能在上传快照中按文件名、Sheet 和单元格范围定位。
- 非法日期、未知人员 ID、无证据字段和超长内容进入明确错误或待确认状态。
- 模型只返回旧 `tasks` 结构时不报错。
- 某个文件失败时保留其他成功文件的模块结果，并在文件级摘要中显示失败原因。
- AI 生成项目名称与当前项目不一致时不得自动替换项目名称，必须人工确认。

## 测试与验收

- 旧的仅工作推进表文件仍能得到相同任务数量和任务字段。
- 一个 Sheet 同时包含项目概况和推进表时，基本信息与任务不串模块。
- 多个文件分别包含基本信息和推进表时，结果能合并到两个模块。
- 表头替换为“建设背景”“预期达成”“工作模块”“实施步骤”等语义变体时仍能正确分流。
- 合并单元格、多行文本和未知列保留证据，不导致任务或项目字段静默丢失。
- 当前基本信息非空时，AI 不会无确认覆盖；空字段可预览补全。
- 历史 `tasks`-only 分析运行仍可读取、预览和应用。
- 前端模块预览、决策按钮、应用按钮和错误提示有组件测试。
- 后端项目立项、负责人提交、数据库迁移和前端构建回归通过。
