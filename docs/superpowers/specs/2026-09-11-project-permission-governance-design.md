# 项目与权限治理设计

## 目标

在不改变现有 API 路径、主要响应字段和既有角色权限结果的前提下，把项目域中分散的身份、角色、生命周期和资源归属判断收口为可测试的统一策略，建立后端权威、前端一致展示、旧数据可兼容、拒绝原因可机器识别的权限基线。

本设计是系统稳定化路线图的第二阶段，只治理项目域及其直接使用的前端项目操作。确认中心、会议状态机、AI 服务、性能和仓库产物治理不在本轮范围内。

## 当前问题

- `bowei_ai_dashboard/app/routers/projects.py` 超过 2500 行，路由、权限、生命周期、事务和兼容逻辑混合。
- `bowei_ai_dashboard/app/permissions.py` 同时承担身份读取、全局能力、项目角色查询、旧字段兼容和多个业务域授权。
- 项目权限判断存在 `_require_*`、`require_project_*`、直接角色集合判断和页面内条件表达式等多种写法。
- `project_members` 已是主要角色来源，但 `projects.owners/coordinator/collaborators` 仍参与过渡期授权回退，使用边界不清晰。
- `company_ceo` 与 `project_ceo` 名称接近但职责不同，分散判断容易造成项目审核权限误继承。
- 前端权限分布在 `permissions.ts`、`taskPermission.ts`、`projectCloseUi.ts` 和页面条件中，存在展示口径漂移风险。
- 多数权限拒绝只有 HTTP 状态码和中文 `detail`，前端缺少稳定机器码。

## 设计原则

### 兼容优先

- 先用特征测试冻结当前允许与拒绝结果，再迁移实现。
- 不在权限收口提交中顺手扩大或收紧角色能力。
- 发现疑似越权或漏权时记录到权限差异清单，另行确认后修改。
- 不改变 API 路径、HTTP 方法、成功响应字段及现有拒绝 `detail` 文案。

### 后端权威

- 前端权限只决定入口、按钮和只读状态，不作为安全边界。
- 所有项目写接口必须在后端通过统一策略授权。
- 当生命周期会改变某个身份的授权范围时（例如公司管理仅可在草稿期直接编辑源数据），由统一策略表达；材料完整性、日期格式、重复申请以及“当前状态能否发生这次转换”等状态机前置条件继续由项目用例处理，并统一返回稳定错误码。

### 主数据优先、旧数据隔离

- `project_members` 是项目角色的主要事实来源。
- 只有当前人员在 `project_members` 中缺少有效角色时，且调用路径明确允许兼容，才从旧字符串字段回退。
- 旧字段解析只存在于兼容模块，Router、Service 和前端不得新增直接读取。

## 方案选择

采用渐进式 Policy 收口，不采用统一装饰器，也不建设数据库可配置 RBAC。

- 纯策略函数能直接覆盖角色矩阵与生命周期组合，不需要数据库或 FastAPI 上下文。
- Service 负责加载身份、项目、角色和资源归属，再调用策略。
- Router 保留参数解析和响应转换，逐批替换原有权限分支。
- 兼容门面使其他业务域可暂时继续调用 `permissions.py`，避免跨域重构。

装饰器方案不采用，因为项目状态和资源归属需要动态加载，容易把业务查询隐藏进框架依赖。数据库 RBAC 不采用，因为当前角色和动作固定，新增权限表、缓存、配置页面与审计超出本轮需求。

## 模块边界

### 后端纯策略

新增 `bowei_ai_dashboard/app/domain/project_permissions.py`，只包含：

- 系统角色、项目角色和项目动作的稳定常量。
- `ProjectPermissionSubject`：当前身份的系统角色、技术管理员标记、项目角色集合和人员标识。
- `ProjectPermissionResource`：项目状态、创建人/申请人等与授权有关的资源属性。
- `PermissionDecision`：`allowed`、`status_code`、`code`、`detail`。
- `decide_project_action(subject, resource, action)`：无副作用的唯一矩阵入口。

纯策略不导入 SQLAlchemy、FastAPI 或 ORM 模型。不存在项目、请求体校验、业务材料完整性等非权限错误仍由 Router/Service 处理。

### 后端访问服务

新增 `bowei_ai_dashboard/app/services/project_access.py`，负责：

- 从账号与人员记录构建权限主体。
- 加载项目并规范化生命周期状态。
- 通过角色兼容模块取得完整项目角色集合。
- 为需要资源归属的动作补充创建人、结束申请人等属性。
- 调用纯策略并返回授权上下文。
- 将拒绝决策转换为兼容 HTTP 错误。

少数现有接口对同一类拒绝使用了不同 `detail`。访问服务允许调用方显式传入经过特征测试锁定的兼容文案覆盖值；稳定错误码仍由策略决定。该覆盖只用于保持外部契约，不允许改变允许/拒绝结果。

该服务只拥有授权相关查询，不接管项目创建、成员变更、结束申请、通知或清理事务。

### 旧角色兼容层

新增 `bowei_ai_dashboard/app/compatibility/project_roles.py`，集中：

- 查询 `project_members` 中的全部角色。
- 判断是否存在有效成员角色数据。
- 在必要时解析旧 `owners/coordinator/collaborators` 字段。
- 返回角色来源 `project_members`、`legacy_fields` 或 `none`，便于测试和后续迁移统计。

兼容回退必须由调用者显式声明，默认关闭。只有当前实现原本支持旧字段授权的读取路径可以开启；当前人员已有有效 `project_members` 角色时不得混入旧角色。严格依赖 `project_members` 的写操作继续保持严格，防止收口过程扩大旧数据权限。

现有 `permissions.py` 中的角色查询函数暂时保留为兼容门面，但内部委托给该模块。项目 Router 不再自行拼接新旧角色来源。

### 稳定错误契约

新增 `bowei_ai_dashboard/app/api_errors.py`：

- `CodedHTTPException` 保留 HTTP 状态码和字符串 `detail`，同时携带稳定 `code`。
- 在 `main.py` 注册专用异常处理器，输出 `{"detail": "原文案", "code": "PROJECT_ACCESS_DENIED"}`。
- 普通 `HTTPException` 和现有异常处理行为保持不变。

项目权限首批错误码固定为：

- `AUTHENTICATION_REQUIRED`：未登录或账号不存在，HTTP 401。
- `ACCOUNT_DISABLED`：账号被禁用，HTTP 403。
- `PROJECT_ACCESS_DENIED`：无项目查看权限，HTTP 403。
- `PROJECT_ACTION_DENIED`：角色不允许执行动作，HTTP 403。
- `PROJECT_STATE_CONFLICT`：现有接口已使用 409 表达的生命周期冲突。
- `PROJECT_RESOURCE_OWNER_REQUIRED`：动作仅允许原申请人，HTTP 403。

前端 `ApiError` 增加只读 `code`，优先读取响应顶层 `code`，无法读取时保持现有消息解析行为。

### 前端展示策略

扩展 `frontend/src/domain/permissions.ts`，以与后端一致的动作名提供纯函数：

- 查看项目与项目管理入口。
- 新建、下发和编辑项目。
- 成员直接维护与成员变更审核。
- 负责人提交、企业教练审核。
- 发起、编辑、撤销和审核结束申请。
- 归档与永久删除。

`taskPermission.ts` 继续负责工作推进域，`projectCloseUi.ts` 的项目结束权限迁移为调用统一项目策略后保留兼容导出。页面逐步删除角色字符串与系统角色的内联组合判断。

## 权限矩阵

角色可多选，判断采用集合包含关系。`super_admin` 由技术管理员身份表示；`company_ceo` 是公司级管理；`project_ceo` 是具体项目的企业教练，二者不互相继承项目审核动作。

| 动作 | 现有允许身份 | 状态约束 |
|---|---|---|
| `project.view` | 超级管理员、公司管理、项目参与角色 | 保持现有草稿和归档可见性 |
| `project.create` | 公司管理、超级管理员 | 无 |
| `project.batch_import` | 超级管理员 | 无 |
| `project.edit_source` | 超级管理员；草稿期公司管理 | 非草稿期直接编辑拒绝 |
| `project.manage_members_direct` | 超级管理员；草稿期公司管理 | 关闭冻结状态拒绝 |
| `project.request_member_change` | 保持现有申请人规则 | 关闭冻结状态拒绝 |
| `project.review_member_change` | 项目企业教练、超级管理员 | 关闭冻结状态拒绝 |
| `project.dispatch` | 公司管理、超级管理员 | 仅 `draft` |
| `project.owner_submit` | 项目负责人、超级管理员 | 仅现有负责人可编辑状态 |
| `project.review_start` | 项目企业教练、超级管理员 | 保持现有审核状态约束 |
| `project.request_close` | 项目负责人、超级管理员 | 仅 `active` |
| `project.edit_close_request` | 原申请负责人、超级管理员 | 仅待审核状态 |
| `project.cancel_close_request` | 原申请负责人、超级管理员 | 仅待审核状态 |
| `project.review_close_request` | 项目企业教练、超级管理员 | 项目 `pending_close` 且申请待审核 |
| `project.archive` | 超级管理员 | 仅 `ended` |
| `project.delete` | 超级管理员 | 保留名称和口令双重确认 |
| `project.technical_kickoff` | 超级管理员 | 保持现有冻结与归档限制 |

矩阵同时记录角色授权和界面动作可用性的状态门禁。纯策略必须处理“状态改变角色权限”的组合；其余状态列由 Router/用例继续校验，前端可据此隐藏当前不可用动作。下发前角色配置、日期格式、结束材料完整性、重复申请等业务校验仍由现有业务逻辑负责。

## 数据流

项目接口的标准授权链路为：

1. Router 解析 `project_id`、请求参数和当前会话。
2. `project_access` 加载账号、项目和角色快照。
3. `project_roles` 优先读取 `project_members`，必要时执行旧字段回退。
4. `decide_project_action` 计算允许或拒绝决策。
5. 拒绝决策转为带稳定错误码的兼容 HTTP 响应。
6. 允许后，现有业务逻辑执行事务、审计和通知。

列表接口使用批量角色映射，禁止在项目循环中逐行查询角色。详情和写接口使用单项目授权上下文。

## 错误与事务边界

- 401 表示认证失败，403 表示身份或资源归属不足，409 表示现有接口已定义为冲突的项目状态。若当前接口把某项状态限制作为 403 权限拒绝，本轮继续保持 403，避免在收口过程中改变外部契约。
- `detail` 保持原有文案，新增顶层 `code`；前端不得用中文文案分支业务逻辑。
- 授权检查发生在任何写入、文件移动、通知和审计记录之前。
- 需要锁定项目或结束申请的接口，在预检查后仍须在加锁读取后复核状态，防止并发越过生命周期门禁。
- 本轮不改变现有事务提交位置，只确保权限服务不执行 `commit`、`rollback` 或外部副作用。

## 迁移顺序

1. 建立后端角色/状态特征测试，冻结当前矩阵。
2. 新增纯策略与矩阵单元测试。
3. 新增旧角色兼容层并把 `permissions.py` 角色查询委托过去。
4. 新增稳定错误响应，不改成功响应。
5. 迁移项目查看、主数据、成员维护接口。
6. 迁移下发、负责人提交、立项审核接口。
7. 迁移结束申请、归档、删除和技术兜底接口。
8. 统一前端项目权限函数及页面调用。
9. 运行完整后端、前端、构建和 CI 静态门禁。

每一步保持可运行并独立提交。旧函数只有在仓库中无调用后才删除；其他业务域使用的确认权限函数不在本轮搬迁。

## 测试设计

### 后端

- 纯策略参数化矩阵：系统角色、项目角色集合、生命周期、资源归属和动作。
- 兼容层：新表优先、旧字段回退、多角色、未知角色、无角色。
- Router 特征测试：每组接口至少覆盖一个允许路径和一个拒绝路径。
- 错误响应：状态码、原 `detail` 和稳定 `code` 同时存在。
- 并发敏感接口：结束审核与归档在锁后复核状态。
- 查询预算：项目列表批量读取角色，防止 N+1 回归。

### 前端

- 纯权限函数表驱动测试，与后端矩阵使用相同动作和角色命名。
- 路由守卫：无入口权限跳转 `/no-access`。
- 项目管理页面：按钮显隐和只读状态与动作决策一致。
- 错误客户端：解析新增 `code`，同时兼容仅有字符串 `detail` 的旧响应。

### 完整门禁

- `python -m pytest tests -q`
- `npm run test:all`
- `npm run build`
- `python -m alembic heads`
- `git diff --check`

本轮不新增数据库迁移。若实现过程中发现必须修改 schema，应停止并单独设计迁移。

## 验收标准

- 项目域 Router 不再新增直接角色字符串组合判断。
- 权限矩阵由一个纯策略入口计算，所有项目写接口均调用统一访问服务。
- `project_members` 优先、旧字段回退的条件、调用范围和来源可测试；写操作不会因引入兼容层获得额外旧字段授权。
- `company_ceo` 不获得 `project_ceo` 的项目审核权限。
- 现有允许/拒绝行为通过特征测试保持不变。
- 权限拒绝响应保留现有 `detail`，并提供稳定 `code`。
- 前端项目入口和操作按钮统一调用项目权限函数。
- 全量测试、构建、迁移单头和差异检查通过。

## 风险与回滚

- 特征测试可能暴露现有规则矛盾：先记录差异，不在迁移提交中改变权限。
- 旧字段回退可能造成误授权：只有 `project_members` 缺失有效角色数据时才回退，并测试来源。
- 角色命名混淆：类型和测试中强制区分 `company_ceo` 与 `project_ceo`。
- 错误响应兼容风险：保留字符串 `detail`，只增加顶层 `code`。
- 大文件冲突风险：按接口组迁移 `projects.py`，每组独立提交并运行聚焦测试。
- 任一阶段出现行为回归，可回退该阶段提交；纯策略和特征测试可独立保留。
