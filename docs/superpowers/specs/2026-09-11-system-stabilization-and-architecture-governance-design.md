# 系统稳定化与架构治理设计

## 目标

用两个连续阶段把当前系统从“功能较完整但基线不可信”推进到“可稳定交付且可持续维护”：

1. 第一阶段恢复可信交付基线，消除数据库、测试、CI 和生产验证中的明确红灯。
2. 第二阶段在保持现有业务行为和外部契约的前提下，渐进拆分超大模块并收拢历史兼容逻辑。

任何阶段结束时，系统都必须保持可启动、可测试、可回滚，不采用一次性重写。

## 当前基线

本设计以 2026-09-11 的工作区检查结果为准：

- 前端 TypeScript 检查和 Vite 生产构建通过。
- 前端 Vitest 共 24 个文件、78 个测试通过。
- `frontend/tests/*.test.mjs` 共 71 个结构与回归测试，其中 12 个失败。
- 后端完整 pytest 共 1821 个通过、12 个跳过、1 个失败。
- 唯一后端失败是 Alembic head 与当前 ORM 在 `tasks.plan_process` 默认值上的 schema 漂移。
- SQLAlchemy 在测试清理时报告 `meetings` 与 `meeting_document_sources` 的循环外键警告。
- CI 对一批已知结构测试失败设有允许名单，其中包含当前迁移一致性失败。
- 后端 `projects.py`、`confirmations.py`、`meetings.py` 和项目初始化 AI 服务体量较大。
- 当前工作区包含用户未提交修改、数据库备份、测试数据目录和临时产物；治理时必须与业务修复隔离。

## 设计原则

### 外部契约稳定

- 不改变现有 API 路径、HTTP 方法和关键响应字段，除非单独形成兼容迁移设计并获得确认。
- 不重命名生产数据库物理表和既有字段；`subtasks` 等历史物理命名通过映射层兼容。
- 不以大规模页面重写解决测试失败，先判断最新业务口径，再选择修实现或修过期测试。
- 前端权限控制只负责展示，最终授权继续由后端执行。

### 数据库定义单一可信

- Alembic migration 是数据库结构演进的唯一交付路径。
- ORM metadata 必须与 `alembic upgrade head` 后的 schema 一致。
- 生产环境不依赖 `create_all` 自动补表或补字段。
- SQLite 用于快速开发测试，PostgreSQL 是生产一致性验收环境。

### 小步提交与可回滚

- 每个修复先增加或校准失败测试，再实施最小改动。
- 每个任务只解决一个可验证问题，并形成独立提交。
- 模块拆分前先固定外部行为测试；拆分过程中不顺带修改业务口径。
- 不把现有用户修改、数据库文件或临时产物混入修复提交。

## 第一阶段：可信交付基线

### 1. 数据库 schema 收口

先明确 `tasks.plan_process` 的期望数据库默认值。建议保留迁移中的空字符串数据库默认值，并在 ORM 增加等价的 `server_default`，因为这能保证通过 ORM 和直接 SQL 创建的记录具有一致行为。修复后必须验证：

- 全新 SQLite 执行 `alembic upgrade head` 成功。
- ORM metadata 与迁移后 schema 完全一致。
- PostgreSQL 从空库执行 `alembic upgrade head` 成功。
- 现有迁移图保持单一 head。

`meetings` 与 `meeting_document_sources` 的双向外键不在同一提交中贸然删除。先增加迁移排序和删除行为测试，再依据真实使用关系选择以下最小方案之一：

- 在 SQLAlchemy metadata 中用 `use_alter` 明确循环依赖；或
- 若业务确认其中一个方向只是冗余引用，另行迁移去除冗余外键。

### 2. 前端回归契约对齐

对 12 个失败逐项建立“最新需求证据表”，来源优先级为：已确认业务设计、当前验收文档、生产页面行为、旧结构测试。每个失败只能采用一种处理方式：

- 当前实现不符合最新口径：修复实现并保留测试。
- 测试断言绑定过时结构或文案：更新为行为断言或新口径断言。
- 测试只验证源代码文本且无法表达用户行为：迁移为 Vitest 组件测试或保留最小结构契约。

重点覆盖登录页、会议上传格式、项目初始化 AI 预览、任务展开与索引、工作推进表和汇报文档格式。

### 3. 统一测试入口

前端新增一个完整测试命令，按顺序运行 Vitest 与 `frontend/tests/*.test.mjs`；CI 和本地文档都调用同一个命令。保留可单独运行的快速单元测试命令，开发者可以快速反馈，但发布门禁必须运行完整命令。

后端保留完整 pytest 入口，并移除 CI 的已知失败允许名单。任何测试失败都必须令 CI 失败；确实无法在 CI 运行的外部集成测试应使用有原因的 skip 标记，而不是把失败名称加入白名单。

### 4. 生产一致性验证

生产门禁至少覆盖：

- 后端编译与完整 pytest。
- 前端完整测试与生产构建。
- PostgreSQL 空库升级到 head。
- 后端健康检查和前端反向代理健康检查。
- 登录、项目初始化、工作推进、工作汇报、确认入库、会议、问题、成果和项目归档的冒烟流程。
- 角色权限矩阵中的允许与拒绝路径。

第一阶段不要求进行大模块拆分。其完成标准是所有门禁全绿、没有允许失败名单、SQLite 与 PostgreSQL schema 一致。

## 第二阶段：渐进式架构治理

### 目标边界

第二阶段解决维护成本，不改变业务功能。治理顺序固定为项目、确认中心、会议、项目初始化 AI、兼容层和前端性能。每个业务域独立设计、独立计划、独立验收，上一域全绿后再进入下一域。

### 后端模块边界

每个大型业务域逐步形成以下职责：

- Router：解析请求、调用用例、转换响应，不直接编排复杂事务。
- Policy：集中角色、项目状态和动作授权规则。
- Service：执行业务用例并拥有事务边界。
- Repository：封装复杂查询和持久化细节。
- Compatibility：集中旧角色、旧状态、旧字段和旧接口映射。

不要求机械地创建五层目录。只有当现有逻辑确实包含对应职责时才提取文件，避免产生空壳抽象。

### 数据流

标准写入链路为：

`HTTP 请求 → Router 校验输入 → Policy 校验身份和状态 → Service 执行业务事务 → Repository 持久化 → 审计/通知 → 响应 DTO`

事务由 Service 统一提交或回滚。通知、附件和 AI 调用若无法与数据库处于同一事务，必须保存可追踪状态，并提供幂等重试或补偿路径。

### 错误处理

- 认证失败、权限拒绝、业务状态冲突、资源不存在和上游 AI 失败使用稳定错误码。
- 前端根据稳定错误码显示中文信息，不依赖后端异常文本做业务判断。
- 服务端日志记录请求路径、业务对象标识和追踪标识，但不记录密码、会话令牌、API 密钥、完整提示词或敏感附件内容。
- 未知异常统一返回通用 500 响应，同时保留服务端堆栈和关联追踪信息。

### 测试结构

测试体系逐步调整为：

- Domain/Policy：纯函数与权限矩阵单元测试。
- Service：SQLite 快速事务测试与关键 PostgreSQL 集成测试。
- Router：认证、授权、状态码和响应契约测试。
- Frontend：组件交互、路由、错误状态和 API mock 测试。
- E2E：只覆盖高价值主流程，不用 E2E 替代所有业务测试。
- 源文本结构测试：仅保留少量防止关键接口或安全配置被误删的约束。

## 性能与工程治理

性能优化安排在正确性门禁之后：

- 保持 ExcelJS 动态导入，测量导出功能实际加载时延后再决定是否替换库。
- 对主入口和大型页面 chunk 建立体积基线，优先拆分低频管理功能。
- 优化前先记录加载、交互和导出指标，避免只按 bundle 文件大小决策。

工程治理包括：

- 为前端补充统一的 `test:all`、lint 和格式检查入口。
- 为后端补充统一的 lint/format 配置，并纳入 CI。
- 增加仓库临时产物分类规则：可提交验收证据、忽略的本地产物、受控数据库备份。
- 当前工作区清理必须先列出目标并确认归属，不自动删除未知文件。

## 计划拆分

为控制风险，实施文档拆成一个总体路线图和四个可独立完成的计划：

1. 可信交付基线：数据库漂移、前端失败、统一测试入口、CI 与 PostgreSQL 门禁。
2. 项目与权限治理：`projects.py`、角色策略、事务和兼容映射。
3. 确认中心与会议治理：确认入库、会议、文档来源和审计链路。
4. 项目初始化 AI、前端性能与仓库治理。

第一个计划是当前立即执行的修复计划。后续三个计划以第一阶段全绿为前置条件，避免在红色基线上重构。

## 验收标准

整个治理目标完成时必须满足：

- 后端完整 pytest、前端完整测试、前端构建全部通过。
- CI 不含失败白名单，所有门禁失败都会阻止合并。
- Alembic head、ORM metadata、全新 SQLite 和 PostgreSQL schema 一致。
- 核心业务冒烟流程及权限拒绝路径通过。
- 三个最大后端路由文件的复杂业务编排已迁移到清晰边界，API 契约保持兼容。
- 历史命名只存在于数据库、兼容层和明确的迁移测试中，不再继续扩散。
- 性能指标不低于治理前基线，低频大依赖不会阻塞初始页面加载。
- 修复提交不包含未经确认的用户文件、数据库备份或临时产物。

## 风险与回滚

- 需求与旧测试冲突：以最新已确认设计和验收文档为准，并在修改测试时记录依据。
- 数据库迁移风险：先在数据库副本和空库演练，不对现有业务库直接试验。
- 模块拆分回归：先固定外部行为测试，每个域独立提交；出现回归时回退该域提交，不影响第一阶段基线。
- 性能优化收益不确定：只有指标证明收益时才保留替换方案。
- 工作区已有修改：所有治理提交显式指定文件，禁止使用宽泛暂存或清理命令。
