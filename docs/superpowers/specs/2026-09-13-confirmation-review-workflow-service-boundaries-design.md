# 确认中心人工审阅工作流服务边界设计

## 目标

将确认中心中不直接写入任务、成果或问题实体的人工审阅命令，从
`bowei_ai_dashboard/app/routers/confirmations.py` 提取到专门的工作流服务。
保持所有 HTTP 路径、状态机、权限、审计事件、通知和响应字段不变，使
Router 只保留 HTTP 输入适配，审阅服务拥有一个命令的一次性事务边界。

这项工作是系统稳定化第二阶段中确认中心域的第一段服务化。它不与已有的
确认中心权限治理重复：权限策略仍复用 `workflow_permissions`、`policy` 与
`workflow`，本次只改变复杂命令的编排归属。

## 已确认现状

`confirmations.py` 目前超过两千行，混合了任务卡 JSON 处理、最终写回、人工
审阅状态流、通知、审计、项目可写性和 HTTP 端点。已有权限治理已使各动作通过
统一决策层受控，但以下人工审阅命令仍由 Router 同时编排鉴权、状态校验、状态
变更、通知和提交：

- 保存、标记需修订、永久不入库、提交人重新提交与撤回；
- 提交单级转交统筹、统筹反馈、上报教练、教练批示、指定负责人；
- 任务卡级确认、退回、转交统筹、统筹反馈、上报教练和教练决策；
- 任务卡转问题中心的现有 `escalation` 服务调用与其审计、通知包装。

最终 `confirm` 命令还写入 Task、SubTask、Achievement 与 Issue，属于独立的
持久化写回事务。本次不将其与人工审阅流同时迁移，避免改变最敏感的写回边界。

## 方案比较

### 方案 A：仅提取 JSON 与通知辅助函数

改动最小，但 Router 仍拥有鉴权、状态转换、审计和提交，不能满足“复杂业务编排
迁移到清晰边界”的架构验收要求。

### 方案 B：分阶段提取人工审阅工作流（采用）

新建 `services/confirmation_review_workflow.py`。服务拥有人工审阅命令的加载、
项目可写判断、权限/状态前置检查、状态写入、审计、通知和一次提交；Router 只
传递 ID、Pydantic payload、当前用户名和 Session。与路由耦合的旧兼容判断以小而
明确的注入回调传入，服务不反向导入 Router。

最终确认写回仍暂留 Router，并在后续独立设计中迁移。这样每一次提交只移动一组
可验证事务，且不会触及 Task/Issue/Achievement 写入语义。

### 方案 C：一次性迁移整个确认中心

能最快减少 Router 行数，但会在同一变更中混合读模型、任务卡、人工工作流和最终
业务写回，难以定位状态或通知回归，不适合作为绿线上的渐进式治理。

## 目标边界

服务公开与现有路由一一对应的用例，按风险分两批实现：

1. 提交单级人工审阅：保存、标记需修订、永久不入库、重新提交、撤回、转交统筹、
   统筹反馈、上报教练、教练批示、指派。
2. 任务卡级人工审阅和转问题中心：确认、退回、转交、反馈、上报、决策、
   `escalate_card_to_issue` 的现有服务调用封装。

服务可以复用 Router 已有的纯 JSON/任务卡辅助函数，但不能以服务导入 Router 的
方式形成循环依赖。共享的任务卡读取、待处理卡检查和提交人/项目解析，先移动到
服务或通过显式回调注入；只在确有复用价值时才建立共享模块。

读取接口、待办计数和最终 `confirm` 写回不在本次范围内。它们维持原路由行为，
后续分别设计。

## 数据流与不变量

标准写入链路为：

`Router → confirmation review workflow → 加载与项目可写校验 → 权限策略 → 状态/卡片前置校验 → 变更 → 审计 → 通知 → 一次提交 → 既有响应 DTO`

必须保持：

- 所有既有 URL、HTTP 方法、返回字段和错误文本/状态码不变；
- 写操作继续受 `require_project_business_writable`、确认中心可见性与现有
  `workflow_permissions` 策略共同限制；
- 任务卡待教练/统筹状态继续阻止不兼容的提交单动作；
- 原有 `OperationLog.action`、通知类型、收件人去重和操作者排除规则不变；
- 每条成功命令恰好一次 `db.commit()`；验证、权限或通知准备失败不得提交半成品；
- `confirm` 对 Task、SubTask、Achievement 与 Issue 的写回本次完全不变。

## 测试与验收

先补服务级边界测试，覆盖：

- 代表性的允许/拒绝角色、项目冻结拒绝与错误状态；
- 提交单状态流：转交、反馈、上报、批示、撤回/重新提交；
- 任务卡状态流和转问题中心的审计/通知不变量；
- Router 对服务的委托与旧兼容回调注入。

迁移每一批后运行相应确认中心回归、权限测试和通知测试；最终运行完整后端 pytest、
前端 `test:all` 与 `build`。验收不仅要求测试通过，还要求 Router 的对应端点成为
单一服务调用，服务不导入 Router，且最终写回路径的原有回归仍通过。

## 非目标

- 不修改数据库 schema、Alembic 或历史 API；
- 不改变确认中心页面布局、前端权限展示或业务状态机；
- 不重写最终确认写回，也不改变 Task、SubTask、Achievement、Issue 的创建规则；
- 不引入异步队列或通知投递机制变更。
