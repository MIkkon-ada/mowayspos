# 项目立项 AI 提取结果恢复与可观测性设计

## 目标

修复项目立项资料导入中“AI 已经返回，但因结构校验失败而每次降级为规则提取”的问题，使 AI 能够处理字段别名、Markdown 包裹和可恢复的结构缺失；当结果确实不可用时，系统仍安全降级，并明确告诉用户失败原因。

本设计只覆盖项目立项资料导入的 AI 提取链路，不改变规则提取的证据约束、项目写入确认机制和既有项目状态流程。

## 当前问题与证据

当前运行记录已经证明 AI 请求本身可以到达模型服务：DeepSeek 请求返回 HTTP 200。但最近项目立项分析运行的调用日志为：

- capability：`project.init.analysis`
- 主模型：数据库模型 id 1
- 错误码：`schema_invalid`
- 最近连续运行均出现相同错误
- 项目运行最终 provider：`local-rule`
- 项目运行最终 model：`structured-spreadsheet-fallback`

当前项目初始化策略只有一个主模型，没有备用模型，最大尝试次数为 1。因此模型返回内容未通过严格结构校验后，会直接落到规则提取。

失败链路位于：

1. `bowei_ai_dashboard/app/services/project_init_ai_pipeline.py` 解析 JSON 并校验 `_RawEnvelope`。
2. `bowei_ai_dashboard/app/ai/service.py` 把校验失败记录为 `schema_invalid`。
3. `project_init_ai_pipeline.py` 捕获 AI 服务错误并返回 `structured-spreadsheet-fallback`。
4. 前端依据 `result_metadata.processing_mode` 显示规则提取提示。

当前模型连接测试只发送 `ping`，不会使用项目导入的提示词、JSON 输出要求和 `_RawEnvelope` 校验，因此“连接测试成功”不能证明项目导入结果可用。

## 设计原则

1. AI 结果必须经过服务端验证，不能为了显示 AI 成功而放宽证据真实性要求。
2. 可恢复的格式问题由系统归一化或请求 AI 修复；来源、人员、日期和任务事实不得由系统臆造。
3. 连接失败、超时、格式错误、证据错误和业务空结果必须分类记录并向用户展示。
4. 规则提取仍是可靠兜底，但只有 AI 多次无法产生可验证结果时才使用。
5. 原始 AI 响应不得在普通日志中泄露 API Key、完整上传内容或敏感个人信息；诊断信息采用结构化、限长、脱敏方式保存。

## 方案比较

### 方案 A：只调整提示词和模型参数

强化 JSON 提示词，增加输出长度，并更换或修正模型名称。

优点是改动小、上线快。缺点是模型输出仍可能带 Markdown、字段别名或少量结构差异，问题会随模型和文件变化再次出现；也无法解释失败原因。

### 方案 B：结构归一化、一次修复请求、备用模型和失败分类（推荐）

在严格校验之前增加安全归一化；首次校验失败时进行一次带字段诊断的修复请求；修复仍失败时按策略尝试备用模型；所有失败原因分类记录，最后才进入规则提取。

优点是针对当前 `schema_invalid` 问题直接有效，同时保留严格证据校验。缺点是增加一次模型调用和少量实现复杂度。

### 方案 C：完整的多模型路由与输出评分

对不同文件类型、任务复杂度和模型历史成功率进行动态路由，并对多个候选结果评分。

优点是长期扩展能力强。缺点是范围过大，会把当前明确的结构校验问题扩展成新的路由系统，暂不适合作为本次修复的第一阶段。

本次采用方案 B，并预留后续增加模型评分和文件类型路由的接口。

## 目标数据流

```text
上传资料
  ↓
文件解析与来源目录生成
  ↓
AI 主模型请求
  ↓
JSON 清理与字段归一化
  ↓
严格结构校验
  ├─ 通过 → 证据修复与业务归一化 → AI 草稿预览
  └─ 失败 → 生成结构诊断
              ↓
          一次 AI 修复请求
              ↓
          再次归一化与校验
          ├─ 通过 → AI 草稿预览
          └─ 失败/不可恢复 → 尝试备用模型
                              ↓
                         仍失败 → 规则提取兜底
```

## 后端设计

### 1. AI 响应归一化器

在 `project_init_ai_pipeline.py` 或独立的同目录模块中增加纯函数归一化层，输入为模型文本和当前来源目录，输出为待校验的 Python 对象及诊断信息。

允许处理：

- JSON 外层包裹 Markdown 代码块。
- JSON 前后存在简短解释文字。
- 可选字段缺失时补充服务端默认值。
- `deadline`、`startDate`、`endDate` 等已批准的兼容字段映射到规范字段。
- `evidence` 中允许模型只输出来源定位的最小字段，摘录由服务端生成。

禁止处理：

- 自动生成不存在的任务、人员、日期或来源。
- 把未知来源映射成当前上传文件。
- 将必需的任务标题、子任务或证据强行填充为虚假内容。
- 静默删除会影响事实含义的字段。

归一化后仍使用严格 Pydantic 合约校验；模型输出包含禁止字段时，只有明确属于兼容别名的字段才允许转换，其余字段进入诊断。

### 2. 结构修复请求

当首次校验失败时，不把原始长文本直接写入普通日志，而是生成受限诊断：

```json
{
  "error_code": "schema_invalid",
  "paths": [
    {"path": "tasks[0].subtasks", "type": "missing"},
    {"path": "project_profile.evidence", "type": "too_short"}
  ]
}
```

修复请求只要求 AI 修复结构，不允许修改已识别的任务标题、人员、日期和 evidence 来源。修复请求必须复用当前批次来源目录，并要求返回同一 JSON 合约。

修复请求最多执行一次，避免无限重试和费用失控。

### 3. 错误分类

统一保留以下错误码：

- `AI_UPSTREAM_CONNECTION`：无法连接模型服务。
- `AI_UPSTREAM_TIMEOUT`：请求超时。
- `AI_UPSTREAM_BAD_REQUEST`：模型或请求参数不被服务端接受。
- `json_malformed`：返回内容不是可解析 JSON。
- `json_missing_or_multiple`：没有唯一 JSON 对象。
- `schema_invalid`：JSON 可解析，但不符合项目立项合约。
- `evidence_invalid`：任务无法绑定真实来源。
- `empty_result`：结果结构合法但没有可用内容。

这些错误码同时用于调用日志、运行结果元数据和前端提示。

### 4. 备用模型策略

将 `project.init.analysis` 的策略调整为支持主模型和备用模型：

- 主模型优先。
- 对连接错误、超时、JSON 格式错误和结构错误允许切换备用模型。
- 对配置错误和明显不支持的请求参数直接停止当前模型尝试并记录原因。
- 每个模型最多执行一次原始请求；每个模型最多执行一次结构修复请求。
- 所有模型均失败后才进入规则提取。

备用模型必须通过项目立项专用的 JSON 合约探测，不以普通 `ping` 成功作为唯一准入条件。

### 5. 连接测试升级

保留轻量连接测试，同时新增“项目立项能力测试”概念。能力测试使用最小化的项目资料样例，验证：

- 模型能够返回 JSON。
- 返回结果能够通过 `_RawEnvelope` 校验。
- 证据结构可以关联样例来源。

系统设置页应分别显示“接口连接正常”和“项目立项结构输出正常”，避免用户把两者混为一谈。

### 6. 可观测性

扩展 AI 调用日志或项目运行元数据，至少记录：

- capability key
- 模型 id 和 revision
- 尝试次数、是否备用模型
- 首次错误码和最终错误码
- 归一化是否执行
- 修复请求是否执行及结果
- 最终处理模式：`ai` 或 `deterministic_fallback`

不保存 API Key。原始响应如确有诊断需要，只保存限长、脱敏后的摘要，并禁止保存完整上传文件内容。

## 前端设计

前端不自行判断 AI 是否可用，只消费后端返回的 `processing_mode`、`failure_reason` 和 `recovery_attempted`。

展示规则：

- AI 成功：`AI 已参与分析，结果仅供核对，确认后再写入。`
- AI 结构修复成功：`AI 已参与分析，系统已自动整理返回格式，请重点核对关键字段。`
- AI 失败并规则兜底：`AI 返回结果未通过结构校验，已切换为规则提取，请重点核对关键字段。`
- 连接或超时失败并规则兜底：`AI 服务暂时不可用，已切换为规则提取，请稍后重试 AI 分析。`

预览页增加“查看分析详情”入口，展示模型、处理模式、失败原因和是否执行过修复，但不展示完整模型原文和敏感资料。

## 测试设计

### 后端单元测试

覆盖以下输入：

1. 标准 JSON，正常通过。
2. Markdown 代码块包裹的 JSON，归一化后通过。
3. 使用兼容字段别名的 JSON，归一化后通过。
4. 缺少任务子任务，首次校验失败并触发修复。
5. 修复后仍缺少证据，进入备用模型或规则兜底。
6. 返回多个 JSON 对象，记录 `json_missing_or_multiple`。
7. 证据来源不在来源目录中，不能被归一化掩盖。
8. 主模型超时后切换备用模型。
9. 主模型结构错误后备用模型成功。
10. 所有模型失败后结果明确为 `deterministic_fallback`。

### 后端集成测试

使用 fake adapter 注入不同模型响应，验证完整的 `process_analysis_run` 流程，包括调用日志、运行元数据和最终 provider/model。

### 前端测试

验证四种提示文案：AI 成功、AI 修复成功、结构错误降级、连接错误降级；同时验证分析详情不会显示敏感模型原文。

### 真实本地验收

使用当前 Excel 文件重新上传，确认：

- 后端至少产生一次 `project.init.analysis` AI 调用。
- 若 AI 输出经过修复并成功，运行结果 provider 不再是 `local-rule`。
- 页面显示 AI 参与或 AI 修复成功提示。
- 只有修复与备用模型都失败时，才出现规则提取提示。

## 不在本次范围内

- 不改变规则提取算法的业务含义。
- 不直接把 AI 结果写入正式项目数据。
- 不自动修改项目负责人、成员或权限。
- 不引入新的外部 AI 厂商。
- 不重做整个项目导入页面，只调整状态信息和分析详情入口。

## 验收结论

本次修复完成的判断标准是：同一份当前导致 `schema_invalid` 的资料，在 AI 返回可恢复的结构差异时能够通过归一化或一次修复完成 AI 草稿；若模型确实无法提供可验证结果，系统必须明确记录原因并安全降级，而不是笼统显示“AI 不可用”。
