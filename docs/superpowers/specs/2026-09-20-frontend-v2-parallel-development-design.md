# 前端 V2 并行开发设计

## 目标

在不影响当前旧前端和后端稳定运行的前提下，创建一个完整复制现有功能的 `frontend-v2`，让 V2 可以独立启动、独立构建、独立进行视觉和交互改造，同时继续复用当前后端 API、认证、权限和数据能力。

## 范围

### 包含

- 在当前仓库内新增独立的 `frontend-v2/` 前端目录。
- 复制当前 `frontend/` 的页面、路由、API 封装、类型、功能组件和测试基础。
- V2 使用独立开发端口 `6005`。
- V2 继续通过 `/api` 访问本地后端 `http://127.0.0.1:8011`。
- 保持登录、退出、权限判断、项目、任务、问题、会议、成果、设置、文件上传下载、AI 能力和语音转写等现有功能。
- 在功能等价的基础上，逐步替换 V2 的布局、主题、组件样式和交互细节。

### 不包含

- 第一阶段不修改后端接口、数据库结构、权限规则或业务逻辑。
- 第一阶段不删除或重构旧的 `frontend/`。
- 第一阶段不把两个前端合并为共享源码包。
- 第一阶段不改变生产环境的前端切换方式。

## 方案选择

### 方案 A：完整复制并独立演进（采用）

将 `frontend/` 复制为 `frontend-v2/`，修改 V2 的包名、开发端口和必要的构建配置。V2 与旧前端共享后端，但源码、依赖安装、构建产物和视觉改造相互隔离。

优点是边界清晰、回退简单，适合先保证功能完整，再逐步改版。缺点是短期内会有两份前端代码，需要在后端接口变化时同步维护。

### 方案 B：旧前端和 V2 共享组件与 API 包

把 API、类型和通用组件抽成共享包，再让两个前端引用。长期可以减少重复，但初期需要先重构当前前端边界，增加启动成本和耦合，不适合作为第一阶段方案。

### 方案 C：在当前前端内通过主题或路由切换实现 V2

不复制目录，而是在同一套源码中维护两套页面或主题。切换方便，但旧版和 V2 会共享大量状态和样式，容易互相影响，不符合本次需要独立试错的目标。

## 运行架构

```text
旧前端 frontend                 新前端 frontend-v2
127.0.0.1:6004                  127.0.0.1:6005
          \                      /
           \                    /
            http://127.0.0.1:8011
                    后端 API
                       |
                 共享开发数据库
```

开发环境中，旧前端和 V2 都通过 Vite 代理 `/api` 请求后端。生产环境暂不切换，待 V2 完成验收后再单独制定发布和回退方案。

## 代码边界

### 旧前端

- `frontend/`：保持现状，仅允许为兼容后端契约进行必要维护。
- 旧前端继续使用现有端口 `6004`。

### 新前端

- `frontend-v2/package.json`：独立包名、命令和依赖入口。
- `frontend-v2/vite.config.ts`：使用端口 `6005`，API 代理目标保持为 `http://127.0.0.1:8011`。
- `frontend-v2/src/api/`：初期保持与旧前端一致，作为 V2 与后端之间的请求边界。
- `frontend-v2/src/types.ts`：初期保持现有接口类型，避免 UI 改造同时引入接口字段变化。
- `frontend-v2/src/pages/`、`src/components/`、`src/features/`、`src/layouts/`：先保证功能等价，后续按模块逐步改造。
- `frontend-v2/tests/`：保留现有契约测试，并在 V2 改变交互行为时补充对应测试。

## 数据流和认证

1. 用户访问旧前端 `6004` 或 V2 `6005`。
2. 前端通过当前统一 API 客户端请求 `/api/*`。
3. Vite 将开发环境的 `/api/*` 代理到后端 `8011`。
4. 浏览器携带现有 `bowei_session` Cookie 完成认证。
5. 前端继续根据 `/api/auth/me`、项目能力和后端权限结果控制页面行为。
6. 文件上传、下载和语音转写 WebSocket 继续使用现有后端路径，单独验证连接和 Cookie 行为。

两个前端共享开发后端和数据库，因此验收数据可能互相可见。所有验证必须使用开发账号和开发数据库，不得把 V2 测试操作指向生产数据。

## 错误处理边界

- 后端业务规则、权限判定、数据校验和错误码由后端继续负责。
- V2 复用现有 API 客户端的 401 处理、错误转换和请求凭据策略。
- UI 改造不得通过隐藏按钮替代后端权限控制。
- 长耗时 AI 请求、文件上传和语音流必须提供加载、失败、重试或取消状态。
- 旧前端不可因为 V2 的构建或运行失败而停止服务。

## 分阶段交付

### 阶段 1：功能等价副本

- 创建 `frontend-v2/`。
- 修改 V2 的包名、端口和启动文档。
- 确认 V2 可以独立安装依赖、启动、登录和访问主要路由。
- 保留 API、类型、页面和测试结构。

### 阶段 2：功能回归

- 验证登录、项目切换、主要列表和详情页面。
- 验证创建、编辑、状态变更等写操作。
- 验证文件上传下载、AI 功能和语音转写。
- 运行契约测试、构建检查和关键浏览器流程。

### 阶段 3：渐进式视觉改造

- 先改 V2 的应用壳、导航、主题变量和基础组件。
- 再按页面逐步改造首页、项目工作台、任务、会议、问题、成果和设置。
- 每个模块改造后保留旧功能行为，并执行该模块的回归检查。

### 阶段 4：切换准备

- 完成 V2 全量验收。
- 记录旧版与 V2 的功能差异。
- 制定生产构建、部署、灰度和回退方案。
- 用户确认后才切换生产入口。

## 第一阶段验收标准

- [ ] `frontend/` 仍可在 `6004` 启动。
- [ ] `frontend-v2/` 可在 `6005` 独立启动。
- [ ] 两个前端都能通过后端 `8011` 登录。
- [ ] V2 可以打开现有主要路由。
- [ ] V2 可以读取项目、任务和用户数据。
- [ ] 至少一条主要写操作在 V2 中完成并能在旧前端看到结果。
- [ ] 文件、AI 和语音相关能力没有被复制过程破坏。
- [ ] V2 构建失败不会影响旧前端运行。
- [ ] V2 的视觉改造可以独立提交和回退。

## 主要风险和控制措施

| 风险 | 控制措施 |
|---|---|
| 两套前端接口类型逐渐不一致 | 后端接口变更时同步检查两个 `src/api/` 和 `types.ts` |
| Cookie 因 host 不一致导致登录失效 | 统一使用 `127.0.0.1`，不要混用 `localhost` |
| 共享数据库导致测试数据互相影响 | 使用独立开发账号和开发数据库，避免生产数据验收 |
| 复制后依赖或路径失效 | 先完成独立安装、构建和启动，再开始视觉改造 |
| V2 改样式影响业务行为 | 视觉提交与业务行为提交分开，优先做页面级回归 |
| 两份代码长期重复维护 | 第一阶段先保证隔离，V2 稳定后再评估抽取共享 API/组件包 |

## 成功标准

V2 在不改变后端业务能力的情况下，能够独立启动并覆盖当前前端的主要功能；旧前端保持可用；后续视觉改造只影响 `frontend-v2/`，不会阻塞旧系统或后端开发。
