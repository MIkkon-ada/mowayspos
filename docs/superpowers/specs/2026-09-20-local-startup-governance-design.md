# 本地启动治理设计

## 目标

让旧前端、V2 前端和本地后端可以用一致、可重复、可验证的方式启动，避免端口白名单、数据库目标和服务未就绪造成“看似启动但实际不可用”。

## 范围

- 保留旧前端 `6004`、V2 前端 `6005`、后端 `8011`。
- 继续使用当前本地 SQLite 数据库，不执行自动迁移、不重置数据、不创建账号。
- 启动成功的定义：后端 `/api/health` 返回 `status=ok`，前端首页返回 HTTP 200，V2 的 API 代理可访问。
- 增加显式停止能力，停止只处理本次启动记录的进程。

## 方案

使用 PowerShell 作为本地启动编排层，批处理文件只负责调用它。启动器先检查端口，再启动后端和前端，轮询健康接口，全部通过后打开 V2 页面；失败时输出具体服务和日志位置。运行状态写入仓库本地的临时目录，并加入忽略规则，避免污染 Git。

后端继续由现有 Python 启动脚本提供，但把 V2 使用的数据库、前端来源和后端绑定地址集中到 V2 启动器中。不会让启动器自动执行数据库迁移，schema 不匹配时直接失败并提示迁移命令。

## 验证

- PowerShell 启动器的静态契约测试覆盖端口、健康 URL、状态文件和超时行为。
- 启动后执行 HTTP 冒烟检查：前端页面、后端健康、V2 `/api/setup/status`。
- 保留现有 V2 build、unit、contract 测试。

## 非目标

- 不改业务 API、权限、数据模型和页面布局。
- 不把旧前端和 V2 合并为一个应用。
- 不在启动阶段自动安装依赖或自动修改数据库。
