# 项目工作推进表 WBS 结构化改造设计

## 1. 目标

将当前工作推进表重构为面向项目管理的“项目工作推进表”，保留现有项目、重点工作、关键任务和执行记录能力，补齐 WBS 识别、交付成果、验收标准、风险跟进和历史进展表达。

本次改造以结构和交互为主，不以迁移或保留当前开发环境中的业务数据为目标。实现和验证可以使用结构化示例数据。

用户界面不直接使用“WBS”作为主称呼。WBS 作为内部层级模型和编号方式，用户界面继续使用“项目工作推进表”“重点工作”“关键任务”等业务语言。

## 2. 范围

### 2.1 包含

- 统一页面名称为“项目工作推进表”。
- 在现有项目 → 重点工作 → 关键任务的基础上建立可识别的 WBS 层级。
- 将计划字段、交付成果、验收标准、责任分工、执行状态、风险和跟进信息组织成统一的视图模型。
- 重构桌面端工作推进表主表，支持层级阅读、筛选、状态识别和关键任务详情入口。
- 让网页主表和 Excel 导出共用同一套字段配置和行模型。
- 在关键任务详情中呈现完整目标、成果、验收、最新进展、下一步、风险/问题和历史跟进。
- 使用示例数据、单元测试、构建和必要的视觉检查验证结构。

### 2.2 不包含

- 不迁移当前开发环境中的真实或历史业务数据。
- 不改变现有登录、权限、提交确认、工作汇报和关键任务执行工作台的业务流程。
- 不要求一次性实现完整的任务依赖网络、资源负荷计算或项目排程算法。
- 不将参考 Excel 的具体公司、人名、日期和文字内容复制进系统。

## 3. 核心概念

### 3.1 WBS 层级

```text
项目
└── 重点工作（工作包/交付方向）
    └── 关键任务（可执行、可验收的末级工作项）
```

WBS 编号用于帮助识别层级，例如 `1`、`1.1`、`1.1.1`。编号是展示和导出的结构信息，不替代数据库主键。

### 3.2 任务完成定义

每个末级关键任务应尽量具备以下信息：

- 做什么：任务名称和所属重点工作；
- 为什么做：任务目标或业务背景；
- 交付什么：成果物；
- 怎样算完成：验收标准；
- 谁负责：负责人和协同人；
- 何时完成：计划开始、计划结束和实际完成时间；
- 当前如何：执行状态、风险/问题、最新进展和下一步。

## 4. 统一字段模型

网页和 Excel 使用同一个业务列配置，不再各自维护一套字段。

### 4.1 主表字段

主表默认字段顺序如下：

```text
WBS编号
重点工作
关键任务
交付成果
验收标准
负责人
计划时间
状态
风险/问题
最新进展
下一步
```

字段配置同时定义：字段 key、显示名称、取值来源、是否默认显示、显示优先级、导出顺序、宽度策略和空值表现。

### 4.2 详情字段

详情中补充完整字段：

- 任务目标；
- 完整交付成果；
- 完成标准/验收条件；
- 负责人、协同人及参与角色；
- 计划开始、计划结束、实际完成时间；
- 当前状态和完成比例（已有数据不足时保持未知，不伪造百分比）；
- 风险描述、阻塞问题、责任人和处理期限；
- 最新确认提交；
- 下一步；
- 历史进展时间线；
- 相关成果、问题、会议和附件入口。

### 4.3 状态与参与角色分离

执行状态和参与方式不混用：

- 执行状态：未开始、进行中、已完成、延期、暂停；
- 风险状态：无风险、有风险、已阻塞；
- 参与方式：主导、辅导、必须参与、按需参与。

参考表中的“部分参与”“按需参与”“无资料”“待确认”等信息，在系统中分别归入执行状态、参与方式或确认状态，不把它们混成一个字段。

## 5. 页面设计

### 5.1 页面顶部

- 页面标题：项目工作推进表；
- 当前项目上下文；
- 项目切换；
- 状态、负责人和关键词筛选；
- 在办/回收站切换；
- 新增重点工作；
- 导出项目工作推进表。

### 5.2 主表

- 重点工作作为父级分组，关键任务作为末级行；
- WBS 编号帮助识别层级；
- 冻结 WBS、重点工作和关键任务等识别列；
- 状态、延期和风险使用清晰但克制的视觉标记；
- 长文本在主表中显示摘要，完整内容进入详情；
- 宽屏显示完整主表，窄屏优先保留任务识别、负责人、状态和下一步，其余字段折叠或横向滚动；
- 不使用空白行或伪 Excel 网格制造“看起来像表格”的空间。

### 5.3 关键任务详情

点击关键任务进入现有执行工作台，并在工作台中增加或整理项目管理字段。详情页是查看完整验收条件、成果、进展历史和风险闭环的主要位置。

## 6. Excel 导出

Excel 导出使用和网页相同的字段配置与行模型：

- 默认导出主表字段，列名和顺序与网页一致；
- 完整文本使用换行显示，不做字符串截断；
- 对长文本采用合理列宽和行高，避免固定行高遮挡内容；
- 保留 WBS 编号和父子层级；
- 保留冻结识别列和表头；
- 状态、风险和缺失信息使用与网页一致的语义；
- 如果需要导出历史进展，作为同一工作簿中的独立“跟进记录”页，不把历史内容强行塞进主表单元格。

## 7. 数据兼容策略

- 现有 `TaskItem` 继续作为重点工作来源。
- 现有 `SubTaskItem` 继续作为关键任务来源。
- 旧数据没有 WBS 编号时，根据当前任务顺序生成展示编号，不修改原始主键。
- 旧数据没有成果、风险或跟进时显示明确空状态，不填入虚构内容。
- 现有最新确认提交、下一步、工作汇报和执行事件继续作为进展来源。
- 只有在主表确实需要而现有接口无法提供时，才新增后端字段或接口；优先通过现有详情数据适配。

## 8. 验证策略

### 8.1 模型测试

- WBS 编号和父子行关系稳定；
- 搜索后层级和行跨度正确；
- 空成果、空验收标准、无进展时的显示一致；
- 状态、风险和延期标记互不覆盖；
- 主表字段配置同时驱动网页和 Excel。

### 8.2 页面测试

- 页面标题和筛选入口正确；
- 重点工作、关键任务和详情入口可用；
- 长文本不破坏行布局；
- 窄屏下保留关键识别信息；
- 导出按钮可用且在数据未加载完时正确禁用。

### 8.3 构建和回归

- 运行工作推进表契约测试；
- 运行相关前端单元测试；
- 运行 TypeScript 构建；
- 使用示例数据检查网页和导出列的一致性；
- 检查现有关键任务执行工作台、回收站和项目权限不回归。

## 9. 实施顺序

1. 建立统一列配置和 WBS 行模型，并补充失败测试。
2. 重构网页工作推进表主表和详情字段映射。
3. 重构 Excel 导出，使其复用统一模型。
4. 补充示例数据和响应式布局验证。
5. 运行完整相关测试、构建和视觉检查。

本设计的完成标准是：用户看到的是清晰的“项目工作推进表”，内部具备可追踪的 WBS 结构，网页和 Excel 的字段来源一致，且不依赖当前开发环境中的旧数据内容。
