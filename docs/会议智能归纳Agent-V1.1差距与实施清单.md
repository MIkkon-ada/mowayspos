# Moways-SOP 会议智能归纳 Agent V1.1 差距与实施清单

> 整理日期：2026-08-07  
> GitHub 基线：`origin/main@fe1b4c9`  
> 需求来源：《Moways-SOP 会议智能归纳 Agent 产品与技术实施规划 V1.0》  
> 用途：本地规划与后续实施依据，当前不代表已开始开发或准备提交。

## 1. 结论先行

当前 GitHub 主分支已有“会议纪要、原始转写保留、纪要版本历史、分析运行模型、证据校验函数”等基础，但还没有形成 V1.0 文档定义的完整 Meeting Agent 闭环。

最合理的实施方式是复用已有模型，按三个可独立验收的阶段推进：

- **P0-A：可信会议纪要**——完整处理长会议，每个重要结论都能回到原文证据。
- **P0-B：任务对照与变更建议**——冻结会前快照，生成字段级 Before/After，但不写回业务数据。
- **P0-C：人工审核与安全写回**——完成权限、过期检查、事务、幂等和审计闭环。

## 2. GitHub 当前能力盘点

### 2.1 已存在且已接入业务流程

- [x] `Meeting` 会议主记录，可保存原始转写、摘要、行动项、决策项和风险项。
- [x] `MeetingRevision` 不可变纪要版本，支持历史版本查看。
- [x] 新建和修改会议时自动追加纪要版本。
- [x] 前端可查看纪要版本历史及当时的原始转写。
- [x] 会议草稿已有创建人、项目 Owner 和 CEO 的可见性控制。
- [x] `/api/meetings/analyze` 能输出基础摘要、成员汇报、行动项、决策/待确认项等结果。
- [x] 项目上下文在 Prompt 中被声明为“仅供关联与核对，不是会议事实”。
- [x] 负责人不在项目成员中时会标记为“待确认”。
- [x] 日期后处理可阻止在原文无年份时凭空补全年份。
- [x] Kickoff Agent 已有快照、提案校验、人工审核和原子写回的参考实现。

### 2.2 已有数据结构，但尚未接入主分析流程

> 以下能力不能算作“已完成功能”；当前主要是数据库模型、Pydantic Schema 和模型级测试。

- [~] `MeetingTranscriptSource`：已有来源类型、原文和哈希，但主接口未创建/管理转写来源。
- [~] `MeetingTranscriptRevision`：已有修订版本和文本哈希，但尚无完整的上传、修订、查询流程。
- [~] `MeetingAnalysisRun`：已有项目快照、模型版本、Prompt 版本、原始输出、规范化输出和校验输出字段，但 `/analyze` 没有持久化 Run。
- [~] `MeetingAnalysisCandidate`：已有候选类型、证据、校验、最终值和审核状态，但无对应 API 和审核界面。
- [~] `validate_evidence()`：可验证字符偏移、引用文本和哈希，但当前主分析结果只依赖自由文本 `evidence_quote`，没有系统化调用该校验。
- [~] `validate_candidate()`：已有部分负责人、验收标准、决策和风险校验，但尚未串联到实际 Meeting Analysis Run。

### 2.3 当前已确认的关键差距

- [ ] 移除 `payload.text[:8000]` 和 `payload.text[:10000]` 截断；当前与“完整会议优先”原则直接冲突。
- [ ] 将一次性 LLM 调用改为 Segment → Chunk → Atomic Facts → Merge → Summary 流水线。
- [ ] 保存每次分析的原始输入、模型原始回包、规范化输出和校验结果。
- [ ] 为所有重要事实保存结构化 `evidence_refs`，不再只保存一段自由文本引用。
- [ ] 建立分块处理清单（coverage manifest），可证明所有原文均已被处理。
- [ ] 增加事实去重、合并、冲突检测和“后续明确替代前述决定”的 supersession 识别。
- [ ] 区分原始说话人标签、AI 匹配候选和人工确认成员，不允许 AI 直接确定身份。
- [ ] 修复当前分析接口将 `confirmed_items` 写入 `risk_items_json` 的字段映射错误。
- [ ] 完整保存 Member Reports；当前分析可返回，但 `Meeting`/纪要保存没有独立结构化字段。
- [ ] 建立标准化 Topics、Decisions、Decision Requests、Action Items、Issues/Risks 输出合同。
- [ ] 建立任务快照、任务匹配、未匹配事项、无变化任务和字段级 Before/After。
- [ ] 建立会议变更提案审核及统一写回；不将 Kickoff 专用写回直接当成通用 Meeting Writeback。
- [ ] 增加过期快照检查、幂等键、完整权限矩阵和审计日志。
- [ ] 前端升级为“证据 / AI 纪要 / 项目变更”三栏审核工作台。

## 3. 数据模型复用与扩展决策

| 能力 | V1.1 决策 | 备注 |
|---|---|---|
| `Meeting` | 复用并逐步扩展 | 保持旧字段兼容，避免一次性改坏现有页面 |
| `MeetingRevision` | 直接复用 | 继续作为人工保存后的不可变纪要快照 |
| `MeetingTranscriptSource` | 复用并扩展 | 补充显示名称、语言、媒体信息、保留策略等必要字段 |
| `MeetingTranscriptRevision` | 直接复用 | 证据必须绑定具体 revision，不只绑定 source |
| `MeetingAnalysisRun` | 复用并扩展 | 增加进度、失败阶段、重试信息、coverage manifest 和成本/用量信息 |
| `MeetingAnalysisCandidate` | 复用为“会议事实候选” | 不与任务变更提案混用 |
| `MeetingSegment` | 新增 | 保存 source/revision、说话人、时间或字符范围、内容和哈希 |
| `MeetingChangeProposal` | 新增 | 保存任务级变更建议、字段 Diff、快照依据、审核和幂等状态 |
| Atomic Facts | P0 先放 Run/Candidate JSON | 暂不新建独立 Fact 表，待查询和统计需求明确后再拆分 |
| Kickoff Agent 表与服务 | 保留 | 仅借鉴快照、校验、审核和写回思路，不在 P0 删除或迁移 |

## 4. P0-A：可信会议纪要

### 4.1 输入与证据层

- [ ] P0 只支持一份“完整转写文本”作为主来源，先不做多音轨融合。
- [ ] 每次分析必须创建或绑定 `MeetingTranscriptSource` 和具体 Revision。
- [ ] 转写内容入库时生成内容哈希，修订后必须创建新 Revision。
- [ ] 定义 `MeetingSegment`：`source_id`、`revision_id`、`segment_no`、`speaker_label`、`speaker_person_id`、`char_start`、`char_end`、`start_ms`、`end_ms`、`text`、`text_hash`。
- [ ] `speaker_person_id` 默认为空；记录映射候选、置信度、映射来源和人工确认人。
- [ ] 定义不可变 EvidenceRef：`source_id`、`revision_id`、`segment_id`、`char_start`、`char_end`、`quote`、`source_hash`，有音频时可加时间戳。
- [ ] 所有重要输出均必须有 `evidence_refs`；没有证据的内容不能伪装为会议事实。

### 4.2 长会议处理流水线

- [ ] 根据说话人、段落和主题边界进行 Segment/Chunk，允许少量重叠以避免上下文断裂。
- [ ] 为每个 Chunk 生成稳定 ID、内容哈希、序号和字符覆盖范围。
- [ ] 为 Run 保存 coverage manifest：全部 Chunk、处理状态、尝试次数、错误、模型与 Prompt 版本。
- [ ] 分块提取原子事实，每条事实必须携带证据和事实类型。
- [ ] 将跨 Chunk 的重复事实合并，但保留全部证据来源。
- [ ] 检测负责人、时间、状态、验收标准和决定内容之间的冲突。
- [ ] 明确区分 `conflict`、`superseded` 和 `needs_confirmation`。
- [ ] 支持 Chunk 级重试、断点恢复、取消和进度查询，不得因一块失败伪造“分析完成”。

### 4.3 结构化输出

- [ ] Executive Summary：只汇总已证实的核心事实。
- [ ] Topics：主题、结论、未决问题及相关证据。
- [ ] Member Reports：原始说话人标签、已确认成员、汇报内容及证据。
- [ ] Decisions：只收录会议已明确作出的决定。
- [ ] Decision Requests：收录明确未决或需指定角色决策的问题，不自动扩大为“需 CEO/教练决策”。
- [ ] Action Items：事项、负责人、时间、验收标准、状态和证据；不明确则“待确认”。
- [ ] Issues/Risks：区分已发生问题、潜在风险和普通计划/进度。
- [ ] 输出经确定性 Validator 后才可进入审核页；校验不通过的字段要清空或标记待确认。

### 4.4 API 与前端

- [ ] 保留现有 `/api/meetings/analyze` 作为过渡接口，不立即删除。
- [ ] 新增转写来源/修订创建与查询 API。
- [ ] 新增 Analysis Run 创建、状态、进度、结果、候选项和失败重试 API。
- [ ] 将长时分析改为后台任务，前端不持有长时 HTTP 请求。
- [ ] 前端先完成“证据 + AI 纪要”双栏，点击证据可定位原文 Segment。
- [ ] 显示分析进度、未处理分块、冲突项和待确认项。
- [ ] 保留现有纪要版本历史，并让每个版本可追溯到 source revision 和 analysis run。

### 4.5 P0-A 验收门槛

- [ ] 任意长度转写都不使用字符切片截断。
- [ ] Coverage Rate = 100%：所有 Chunk 均有成功或显式失败记录，只有全部成功才标记 Run 完成。
- [ ] 重要输出 Evidence Coverage = 100%。
- [ ] Unsupported Claim Rate = 0。
- [ ] 所有 EvidenceRef 的 Revision、字符范围、引用和哈希校验通过。
- [ ] 当前已知的风险字段映射错误有回归测试并修复。
- [ ] “8月3日前”不被改写为“8月3日”；原文无年份时不补年份。
- [ ] 不明确的负责人、日期、验收标准和决策状态全部进入“待确认”。
- [ ] 重试不会丢失已完成 Chunk，也不会重复创建最终结果。

## 5. P0-B：任务对照与变更建议

### 5.1 会前快照

- [ ] 分析开始时冻结项目、重点工作、关键任务、负责人、计划时间、状态、完成标准和备注。
- [ ] 快照包含稳定记录 ID、字段值、版本/更新时间和整体哈希。
- [ ] 会议分析后不再重新读取当前数据冒充 Before。
- [ ] 项目上下文只用于匹配和对照，不能被收录为会议证据。

### 5.2 任务匹配

- [ ] 匹配优先级：原文明确 ID/编号 → 明确标题 → 负责人+内容 → 候选集人工确认。
- [ ] 不足以唯一确定时 `matched_task_id = null`，不强行归属。
- [ ] 记录匹配理由、候选任务、置信度和对应证据。
- [ ] 区分“未匹配新事项”与“可能属于现有任务但待确认”。
- [ ] 用 Gold Dataset 单独验证任务匹配，不与纪要摘要质量混在一个总分中。

### 5.3 字段级变更提案

- [ ] 每个任务一张提案卡，卡内可包含多个字段 Diff。
- [ ] 每个 Diff 保存 `field`、`before`、`after`、`reason`、`evidence_refs`、`validation_status`。
- [ ] 支持的操作和字段采用白名单；未开放字段直接阻断。
- [ ] 展示“已变更”、“讨论过但无变更”、“未讨论”和“无法匹配”四类结果。
- [ ] AI 只生成建议，P0-B 不修改任何项目业务数据。

### 5.4 P0-B 验收门槛

- [ ] Task Match Accuracy ≥ 95%，并单独统计“错误强匹配”比例。
- [ ] Change Precision ≥ 95%，且每个建议字段均有原文证据。
- [ ] 不明确的变更不生成确定 After，而是标记待确认。
- [ ] 无变化和未讨论任务可被完整列出，不因只展示建议卡而形成假覆盖感。

## 6. P0-C：人工审核与安全写回

### 6.1 审核与权限

- [ ] 明确角色矩阵：谁可查看证据、修改提案、批准、执行写回和查看审计记录。
- [ ] 每个提案和字段可接受、修改、忽略或标记待确认。
- [ ] 保留 AI 原始建议、人工最终值、修改差异、审核人、时间和评论。
- [ ] 证据查看权限不得高于原会议源文件的访问权限。

### 6.2 写回安全

- [ ] 写回前重新读取目标任务并逐字段对比 Before。
- [ ] 任一被选中变更的 Before 已过期时，整批中止并返回冲突清单。
- [ ] 写回前重新执行字段白名单、所属项目、权限和业务规则校验。
- [ ] 所有选中提案在同一数据库事务中写入；任一失败全部回滚。
- [ ] 每次写回要求幂等键，重复请求不重复应用。
- [ ] 写回结果记录 Run、Proposal、操作人、目标记录、Before/After 和事务结果。
- [ ] AI 分析、人工审核和正式写回三个动作使用独立状态，不得混为一个“已完成”。

### 6.3 P0-C 验收门槛

- [ ] AI 没有任何可绕过人工审核直接写回的接口路径。
- [ ] 无权用户不能审核或写回。
- [ ] 过期快照必须被阻止，且不产生部分写入。
- [ ] 模拟中途数据库失败时，所有目标记录保持写回前状态。
- [ ] 相同幂等键重复请求只产生一次有效变更。
- [ ] 每个已写回字段都能追溯至人工批准的 Proposal 和原始会议证据。

## 7. 质量数据集与测试清单

- [ ] 建立小型 Gold Dataset，首批建议不少于 10 场、覆盖短/长会议及不同会议类型。
- [ ] 每场人工标注 Segment 覆盖、说话人、原子事实、决策、行动项、风险、冲突和证据。
- [ ] 有任务对照的样本标注正确任务 ID、字段 Before/After 和“不应变更”项。
- [ ] 覆盖重复讨论、前后冲突、明确改口、无负责人、无日期、模糊日期、实际问题被误分为风险等边界情况。
- [ ] 将确定性校验、服务层、API、权限、事务和前端结构测试分层。
- [ ] 每次更换模型、Prompt 或合并规则时运行同一套评测，保存版本化结果。
- [ ] 指标分类统计，不用单一总分掩盖“某一类事实经常错”。

## 8. 安全、隐私与运维补充

- [ ] 定义音频、转写、Segment、分析原始回包和证据的保留期。
- [ ] 定义删除/匿名化策略，并处理已有纪要版本中的派生数据。
- [ ] 记录证据访问、下载、审核和写回操作。
- [ ] 敏感内容不出现在普通应用日志、异常堆栈或前端埋点中。
- [ ] 定义长会议分析的模型用量、单次成本上限、超时和重试上限。
- [ ] 建立 Run 级可观测性：总耗时、Chunk 数、成功/失败数、重试次数、Token/费用和最终状态。

## 9. 明确延后，不进入本轮 P0

- [ ] 会议实时转录。
- [ ] 多人独立音轨自动对齐。
- [ ] 多来源事实融合与来源优先级裁决。
- [ ] 声纹自动确认人员身份。
- [ ] 知识图谱和跨会议长期记忆。
- [ ] 无人审核的自动任务写回。
- [ ] 在通用 Meeting Agent 稳定前删除或大规模迁移 Kickoff Agent。

## 10. 开发前必须定下的决策

- [ ] P0 完整转写的最大允许规模，以及对应的 Chunk 上限。
- [ ] `MeetingSegment` 是否首期入独立表；建议入表，因为证据定位和说话人确认需要稳定 ID。
- [ ] coverage manifest 首期保存在 Run JSON 还是独立 Chunk 表；建议 P0 先 JSON，只在运维查询需求上升时拆表。
- [ ] 后台任务执行方式：现有进程内任务、独立 Worker 或队列。
- [ ] 会议事实 Candidate 与任务 Change Proposal 的状态机和关联方式。
- [ ] 哪些项目字段允许被提案，哪些字段始终禁止 Meeting Agent 修改。
- [ ] 审核人和写回人的具体角色范围。
- [ ] Gold Dataset 的数据脱敏、保留和人工标注负责人。

## 11. 建议执行顺序

1. 固化 GitHub `main` 基线、补当前已知错误的回归测试。
2. 把现有模型真正接入 Source/Revision/Analysis Run 持久化流程。
3. 实现 Segment、EvidenceRef 和不可变证据校验。
4. 实现无截断的 Chunk 分析、coverage manifest 和断点重试。
5. 实现 Atomic Fact 合并、冲突/supersession 检测和全局纪要。
6. 完成 P0-A 双栏审阅页和 Gold Dataset 验收。
7. 增加会前任务快照与可解释匹配。
8. 生成任务级、字段级 Before/After，完成 P0-B 只读审核。
9. 完成审核权限、过期检查、原子写回、幂等和审计。
10. P0-C 验收通过后，再评估音频、实时转录和多来源融合。

## 12. 实施时的底线

- 不从旧的本地未合并提交整批恢复功能；以最新 GitHub `main` 为开发基线，只重新实现已确认有价值的设计。
- 不重复新建已经存在的 Transcript Source、Transcript Revision、Analysis Run 和 Meeting Revision 体系。
- 不为追求“看起来完整”而隐藏失败 Chunk、冲突事实或待确认字段。
- 不将项目上下文、AI 常识或当前数据库状态冒充为会议事实。
- 不允许 AI 绕过人工确认修改项目业务数据。
