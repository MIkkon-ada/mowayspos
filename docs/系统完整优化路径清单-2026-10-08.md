# MOWAYS 项目管理系统完整优化路径清单

编制日期：2026-10-08
适用范围：`frontend-v2`、FastAPI 后端、AI 处理流程、数据与发布运维。
文档性质：后续优化路线图与任务清单；不代表全部项目均有缺陷，也不代表已经实施或通过测试。

## 一、目标与使用方法

优化目标：让用户知道下一步做什么，让一次汇报有效更新项目，让 AI 结果有依据、可审核，让系统在持续迭代中保持稳定。

本清单分为 7 个阶段、32 项任务。每项都包含实施动作、验收要求、依赖和工作量级。执行时按编号选择小批次，不建议一次性改完整个系统。

使用规则：

1. 每项先核对当前实现；已实现且验收通过的内容直接标记完成，仅补实际缺口。
2. 勾选代表实施、验证和证据记录均完成；单纯写完代码不勾选。
3. 每项开工时补充负责人、实际范围、目标版本；完成时记录测试结果和遗留事项。
4. 优先级：P0 为数据、权限和发布正确性；P1 为核心业务效率与可靠性；P2 为体验一致性、效率提升与后续能力。
5. 工作量：S 为局部改动；M 为单模块前后端改动；L 为跨模块、迁移或生命周期改动。这是范围提示，不是工期承诺；实测后再排期。
6. “核查项”必须先得到复现、数据或业务依据，不能把建议直接当成已经证实的缺陷。
7. 当前路线图以主智能体或开发者逐项执行为默认，不包含调用子代理或创建其他聊天任务的授权。

### 2.2 必须保持的业务与界面约束

- 业务主结构固定为“项目 → 重点工作 → 关键任务”；过程记录不增加为第四层主结构。底层历史字段名须通过映射理解，不能仅凭 `Task`、`SubTask` 名称推断业务层级。
- 公司管理负责项目入口与全局查看；企业教练负责方向、重大事项和规定的审核；PM 负责日常推进、汇报确认与闭环；统筹人不默认拥有最终确认权；责任人与协助人分别表达。任何新增动作都要核对该项目内的实际角色。
- 前端隐藏按钮不能替代后端权限。新增汇总接口也必须使用服务端当前身份和项目范围。
- AI 分析结果先形成建议，由有权限的人确认后进入正式业务数据。项目初始化、启动会和执行期汇报的写入规则分别处理。
- 工作推进表保留重点工作分组、独立的“最新进展”和“下一步计划”、重点工作验收标准详情入口、可折叠项目总体标准。
- 不增加已明确取消的 WBS 显示、独立交付成果列、重复项目选择入口或无实际用途的“项目工作区”。“导出 Excel”“新增重点工作”继续收纳到操作菜单。
- 下拉、展开和收起方向使用 SVG 图标组件，优先复用 `ChevronDownIcon`；中文文案和编码保持正常。
- 当前工作区存在多项未提交开发成果。实施前检查差异，不能用整库重置、覆盖或批量提交混合改动来推进优化。

### C. AI 可靠性与可审核性

- [ ] **C01｜建立可重复的 AI 业务评测集｜P1｜M**

| 页面可操作时间    | 指定设备、网络、数据规模下冷/热启动分别测量      | 可先以高频页 P95 不超过 2 秒作为讨论目标     |
| 常规读取接口     | 排除 AI 长任务和大型文件导出，记录 API P95 | 可先以测试环境 P95 不超过 500 毫秒作为讨论目标 |
| AI 长任务反馈   | 提交后到首次状态可见时间；阶段耗时与失败分布      | 不长时间无反馈；可查询真实状态；失败可定位与重试     |
| 恢复能力       | 重启任务进程、恢复备份、应用回退演练          | 数据不重复不串项目，恢复时间符合约定           |
| 回归质量       | 本批关联测试、核心流程和发布检查            | 无未解释失败；清楚记录未覆盖范围             |

AI 耗时需按字数、页数、音频时长和输入类型分组统计。样本少时报告样本数与原始耗时，不将少量样本的 P95 当作稳定服务水平。
